# 바라 설치·연결 자동화와 트레이 운영 Implementation Plan

> **For agentic workers:** 구현 승인을 받은 뒤 `superpowers:subagent-driven-development` 또는 `superpowers:executing-plans`로 작업 단위별 구현·검증을 수행한다. 이 문서는 계획이며 구현을 시작하는 지시가 아니다.

**Goal:** 비개발자가 바라를 설치·연결하고, 하나의 앱을 펫 또는 트레이로 조용히 사용하며 데이터를 보존해 업데이트하거나 선택한 범위로 제거할 수 있게 한다.

**Architecture:** 기존 Tauri 호스트와 Bun 제어 프로세스가 앱 소유 로컬 메모리 서버를 계속 함께 관리한다. 설치·연결의 상태 관리와 정책은 TypeScript에 두고 Windows 창·트레이·IPC·프로세스·비밀 보관은 얇은 네이티브 경계로 처리한다. 외부 MCP 연결기는 실행 중인 바라에 전달만 하며 메모리 엔진을 독립 실행하지 않는다.

**Tech Stack:** 현재 TypeScript/Bun, Hono, bun:sqlite, Tauri/Windows, 기존 Discord SDK와 MCP 구현. 새 의존성 추가는 이 계획의 자동 승인에 포함하지 않는다.

**Spec:** [사용자 요구사항과 제품 설계](2026-10-04-onboarding-tray-spec.md). 그 문서의 U1–U9는 확정 요구사항, 세부 기본값은 검토 가능한 제안이다.

**상태 (2026-10-08):** `main`의 `d198dbb7`, 제품 0.1.1 기준으로 단계 1·2·4와 7A 일부·7B 주요 기능을 구현했다. Windows 검증이 남아 있어 전체 완료는 아니다. 최신 범위는 1.3절과 [검증 기록](../verification.md)을 따른다. 단계 3·5·6은 보류, 7C는 미구현이다. 아래 체크리스트에서 미체크는 미구현뿐 아니라 일부 구현·검증 대기도 포함하므로 괄호의 상태와 함께 읽는다.

## Global Constraints

- 로컬 메모리 서버는 바라 앱과 함께 시작·종료한다. 독립 서비스·숨겨진 엔진 자동 기동을 추가하지 않는다.
- 펫 숨김은 표시 모드 변경이다. 실행 접근점으로 트레이를 남기고, 직접 요청한 결과만 작은 말풍선으로 표시한다.
- 원격/기존 외부 서버와 다른 앱이 소유한 AI·봇 프로세스는 종료하지 않는다.
- 새 제품 로직은 `apps/` 아래 TypeScript/Bun으로 작성한다. Rust는 필요한 Windows 경계에 한정한다. Python·ORM·새 HTTP 프레임워크를 추가하지 않는다.
- 일반 사용·설정·업데이트에서는 기존 설치·DB·자격·초안·외부 앱 설정을 보존한다. 명시적으로 선택한 제거의 범위는 설계 4.8절을 따른다. 저장 결과가 불확실하면 자동 재전송하지 않는다.
- 업데이트와 제거를 분리한다. 데이터 형식 변경 전 검증된 복구 지점을 만들고, 완전 삭제는 명시적으로 선택한 앱 소유 로컬 데이터에만 적용한다. 새 버전의 사용자 쓰기를 받은 뒤 이전 백업을 자동 복원하지 않는다.
- 새 UI 문구는 `messages.ts`, 네이티브 문구는 `native-host.json`을 사용한다. 민감한 값을 UI·일반 로그·명령 인자에 넣지 않는다.
- 실제 구현체와 임시 데이터로 검사한다. 가짜 Store·Embedding 구현체를 만들지 않으며 기존 데이터·운영 서버를 테스트에 사용하지 않는다.
- 단계마다 관련 테스트, 타입 검사, UI/서비스 빌드, 변경한 Rust 검사와 실제 Windows 동작을 확인한다. 설치 파일 검증과 개발 실행 검증을 구분한다.
- 아래 새 파일·타입·명령은 **구현 제안**이다. 이미 존재하는 기능으로 간주하지 않는다.

## Review Focus

1. **숨김 복원 중 트레이 실패:** 접근할 창과 트레이가 모두 사라진 채 서버만 남지 않아야 한다. 단계 1의 시작 실패 검사로 검증한다.
2. **트레이 클릭·펫 재클릭·초점 이동 경합:** 메뉴 명령은 한 번 실행하고 입력창이 바로 다시 닫히지 않아야 한다. 단계 1의 실제 이벤트 순서 검사로 검증한다.
3. **숨긴 펫의 옛 좌표·백그라운드 피드백:** 사용자 요청 결과는 올바른 모니터에 나타나고 자동 작업은 팝업을 만들지 않아야 한다. 단계 1의 위치·출처별 검사로 검증한다.
4. **승인/토큰 전달 중 응답 유실·재실행:** 다른 기기는 회수할 수 없고 같은 기기는 중복 발급 없이 회복해야 한다. 단계 3·5의 실제 저장소 및 IPC 검사로 검증한다.
5. **설치 중단·설정 파일 동시 수정·종료 중 저장:** 기존 데이터·다른 MCP 항목·미확정 입력이 유실되지 않아야 한다. 단계 1·2·5·6의 실패 주입·재시작 검사로 검증한다.
6. **업데이트 전 DB 열기·중간 실패·같은/낮은 버전 설치:** 최초 마이그레이션 전에 DB 스냅샷과 글 형식 내보내기를 끝내고, 실패 시 글 형식 가져오기로 복구한다. 단계 7의 실제 A→B 설치와 실패 복구로 검증한다.
7. **글 형식 백업의 무손실·개수 일치:** 내보내기→가져오기 왕복 후 기억·관계·별칭·시각·첨부가 원본과 일치하고, 저장 게이트가 개수를 바꾸지 않아야 한다. 단계 7B의 왕복 검사로 검증한다.
8. **완전 삭제의 경로·정션·외부 등록·파일 잠금:** 앱 소유 데이터만 제거하고 남은 항목을 정확히 표시한다. 단계 7의 두 제거 모드와 경계 검사로 검증한다.

### 1.1 확정한 진행 순서 (2026-10-06 사용자 결정)

이 절은 2026-10-06 결정 이력이다. 지인 체험 시점과 선행 조건은 **1.2절의 2026-10-07 결정이 우선**하며, 현재 작업 상태는 1.3절을 따른다. 당시에는 사용자 혼자 사용한 뒤 날짜를 정하지 않은 지인 체험으로 사용감을 듣기로 하고 다음 순서를 정했다.

| 순서 | 작업 | 목적 |
|---|---|---|
| 1 | 단계 1 | 본인 사용 편의, 이후 단계의 기반 |
| 2 | 단계 4 (설정 화면에 먼저) | 본인 사용 편의. 단계 2의 AI 선택 단계가 같은 화면을 재사용한다 |
| 3 | 단계 2 + 7A의 버전·소유 경로 기록 | 지인이 개발 도구 없이 설치할 수 있게 한다 |
| — | **지인 체험** | 실제 사용감 수집 |
| 4 | 피드백 반영 + 7B 업데이트 연결·7C 제거 | 데이터 보존 업데이트와 범위가 명확한 제거 |
| 5 | 단계 3·5·6 | 체험 피드백을 본 뒤 필요와 순서를 다시 정한다 |

- 단계 1 안에서는 1A → 1B → 1C(그리기 중단 → 종료 정리 → 서버 시작 분리) 순서로 한다. 처음에는 서버 시작 분리를 1B보다 먼저 두었으나, 앱이 시작할 때 메인 창을 숨긴 채 항상 만들어 시작 검사가 펫 표시 여부와 무관하게 실행됨을 확인해 순서를 바꿨다(2026-10-06). 서버 시작 분리는 메인 창 화면 로드 실패에 대비하는 보강이다.
- 단계 4를 단계 2보다 먼저 한다. 마법사 안에 AI 선택 화면을 따로 만들지 않고 설정 화면의 선택 UI를 재사용한다.
- 지인 체험은 다른 사람의 PC에 배포하는 일이므로 단계 2를 전제로 한다. 7B·7C는 다음 근거로 체험 뒤에 둔다: 현재 후속 DB 마이그레이션이 없어 업데이트는 프로그램 파일 교체에 그치고(F18), "프로그램만 제거"의 데이터 보존은 0.1.0에서 검증했다(F19).
- **지켜야 할 조건:** 지인에게 DB 형식을 바꾸는 업데이트를 처음 배포하기 전에 7B(업데이트 전 자동 백업과 실패 복구 안내)를 끝낸다. 처음에는 글 형식 백업·복원이 터미널 명령뿐이어서 비개발자가 직접 실행할 수 없었다. 2026-10-07 설정 화면에 백업 만들기와 백업에서 되살리기(직접 만든 백업·업데이트 전 백업 목록에서 고름)를 넣었다(`docs/status.md`, 실제 Windows 확인 대기).
- 각 배포는 그 시점에 완료한 기능만 성공으로 표시하고, 아직 지원하지 않는 선택지는 노출하지 않는다.

### 1.2 지인 체험 시점 변경 (2026-10-07 사용자 결정)

당분간 사용자가 설치판으로 혼자 쓰며 개발을 이어 간다. 지인에게는 "안전하고 안내문 없이도 쉬운" 상태가 된 뒤에 준다. 1.1절의 "7B·7C는 체험 뒤" 판단을 바꿔, 다음을 지인 체험 전 조건으로 둔다.

- 안전: 1C③ 종료 정리, 화면에서 쓰는 백업 내보내기, 7B(업데이트 전 자동 백업·실패 복구 안내), 깨끗한 Windows 환경(Sandbox·가상머신 등)에서 처음부터 설치 검증, 메모리 서버의 데이터 초기화 누락 수정(2026-10-07 반영, status.md).
- 쉬움: 설치 마법사의 디스크 여유 공간 확인과 모델 다운로드 진행률, 사용자가 직접 쓰며 모은 불편 사항 반영. 지인은 안내문을 읽지 않는다는 전제로 화면만으로 다음 행동을 알 수 있어야 한다.
- 라이선스: Spine 쪽 조건은 사용자의 유료 Spine Editor 라이선스와 런타임 `LICENSE` 동봉으로 충족한다(펫 Spine 설계 U13). 펫을 AGPL-3.0-only로 받는 사람에게 Spine 런타임이 섞인 결과를 설명하는 추가 허가 문구(같은 설계 O14)는 아직 정하지 않았고, 다른 사람에게 배포하거나 저장소를 공개하기 전에 정한다.
- 정한 순서: 1C③ → 마법사 보완(디스크·진행률) → 화면 백업 내보내기 → 7B → 사용하며 모은 불편 사항. 2026-10-08 확인 기준으로 앞의 작업과 7B의 업데이트 전 백업·화면 복원까지 코드 반영됐다. 남은 검증과 구현은 아래 1.3절을 따른다. 단계 3·5·6은 계속 보류한다.

## 2. 계획에서 고정할 공통 계약

다음 이름과 의미를 세부 구현에서 공유한다. 기존 설정 파일은 명시적 마이그레이션 또는 안전한 기본값으로 읽고, 알 수 없는 새 버전은 덮어쓰지 않는다.

```ts
type DisplayMode = "pet" | "tray"; // 저장하는 사용자 선택
type TrayAction = "input" | "search" | "dashboard" | "settings"
  | "recent-result" | "toggle-pet" | "quit";
type RequestOrigin = "user" | "background";
type SetupStepState = "not-started" | "working" | "ready" | "attention";
type IntegrationKind = "mcp-codex" | "mcp-claude-code" | "discord";
interface IntegrationStatus {
  id: string;
  kind: IntegrationKind;
  state: SetupStepState;
  message: string; // 사용자용, 비밀값 없음
}
```

- `DisplayMode`와 실제 창 표시 상태는 구분한다. 저장 실패나 트레이 생성 실패를 성공한 숨김 상태로 표시하지 않는다.
- `RequestOrigin`은 사용자가 요청을 시작한 통로에서 부여하고 요청 ID와 함께 보존한다. AI 출력에서 읽지 않는다.
- 새 연결은 설치별 `installationId`, 외부 앱별 `integrationId`로 구분한다. 현재 토큰의 ID를 일괄 변경하지 않는다.
- 공개 설정은 연결 상태·토큰 보유 여부만 포함한다. 토큰과 개인키·회수 증명은 비공개 저장 경계에 둔다.
- 유지보수 기록은 앱 버전·payload 파일 목록·DB/설정 형식 버전·설치 ID·앱 소유 경로·진행 단계·복구 지점·자동 실행 상태·관리한 외부 등록을 구분한다. 제거 모드는 `keep-data` / `remove-local-data`로 기록하고 업데이트를 제거 모드로 취급하지 않는다. 평문 비밀값을 유지보수 기록에 넣지 않는다.

- [ ] 7C. 기본·사용자 지정·레거시 데이터 경로와 링크를 검증한다. 최종 경로가 앱 소유 범위를 벗어나면 삭제하지 않는다. 잠긴 파일·불명확한 소유권은 남은 경로/이유로 표시하고 재시도·재부팅 후 처리를 검증한다.
- [ ] 7D. 버전이 실제로 다른 설치 파일 A와 B를 만들어 격리된 Windows 사용자/VM에서 설치→사용→업데이트→재실행→각 제거 모드를 검사한다. 정리 실패를 포함한 최종 산출물 검증과 관련 검사 통과 후 리뷰·커밋한다. 이 작업에서 실제 사용자 데이터를 제거하거나 운영 서버 자격을 폐기하지 않는다.

**완료 기준**

- A→B 뒤 기억·첨부·초안·연결 자격·표시 모드·자동 실행 상태가 유지되고 폐기된 앱 파일은 없다. 일반 사용자 추가 파일과 다른 프로그램은 보존된다.
- 다운로드/복사/백업/마이그레이션/시작 검사 중 각 실패와 디스크 부족·강제 종료 후에도 기존 데이터를 잃지 않고 재개 또는 일관된 복구가 가능하다. 정상 사용 이후 새로 기록한 기억을 자동 롤백으로 지우지 않는다.
- 프로그램만 제거 후 앱 소유 프로세스·실행 등록은 없고, 재설치하면 보존된 기억과 설정을 이어 쓴다. 유지한다고 알린 데이터 파일은 제거 전후 해시 또는 논리 내용이 일치한다.
- 로컬 완전 제거 후 확인한 앱 소유 DB·첨부·모델·초안·암호화 자격·내부 백업은 없고, 별도 내보낸 백업·원본 키·외부 서버 기억·다른 앱 설정은 남는다.
- 제거기가 실제 Bara/Pet 경로를 처리하며 기본 NSIS의 다른 데이터 경로만 정리하고 완료했다고 표시하지 않는다. 공유 폴더·드라이브 루트·정션 밖 대상은 변경되지 않는다.
- 온라인에서 소유 통합 등록이 해제되며, 오프라인·권한 부족·변경된 MCP 항목·잠긴 파일은 미완료로 정확히 표시한다. 재설치/등록 재개에서도 중복 자식 프로세스나 활성 등록이 누적되지 않는다.

## 5. 주요 위험과 대응

- **보이지 않는 실행:** 트레이 성공 전에 유일한 창을 숨기지 않는다. 종료 중에도 표시를 유지한다.
- **자동화가 비밀값 노출로 바뀜:** 일회 연결과 제한 토큰을 사용하고, MCP 설정에는 비밀값 없는 연결 명령만 남긴다.
- **중단 뒤 빈 데이터로 성공 처리:** 기존 설치 journal·DB 소유권 검사를 재사용하고 데이터 삭제를 복구 수단으로 사용하지 않는다.
- **외부 설정 손상:** 지원 버전을 확인하고 Bara 항목만 변경한다. 동시 수정은 중단·재읽기로 처리한다.
- **파일 교체와 데이터 변환의 불일치:** 최초 데이터 변경 전 DB 스냅샷과 글 형식 백업을 검증하고, 실패 시 글 형식 가져오기로 복구한다. 정상 사용 뒤 과거 백업으로 자동 복원하지 않는다.
- **글 형식 백업의 누락:** 무손실 목록에서 빠진 항목은 복구 때 조용히 사라진다. 새 테이블·필드를 추가하는 변경은 내보내기 대상 여부를 함께 결정하고 왕복 검사를 갱신한다. 재계산 시간은 실측값으로 안내한다.
- **제거 범위 오판:** 앱 소유 목록·최종 경로·사용자 선택을 함께 확인한다. 외부 등록은 자격을 지우기 전에 처리하고, 남은 항목은 완료와 구분한다.
- **범위 확대:** Discord는 선택 단계, 원격 신규 설치는 이미 가진 서버만 대상으로 한다. 독립 메모리 데몬과 다중 사용자 서비스는 제외한다.

## 6. 계획 검토 후의 진행 원칙

이 계획에서 구현을 자동으로 시작하지 않는다. 2026-10-06 사용자가 1.1절의 순서로 진행을 요청했다. 단계 1의 1A부터 시작하며, 새 작업 사본에서 각 작업의 실패 검사→최소 구현→관련 검증→독립 리뷰 순으로 진행한다. 단계 1의 수명/표시 계약과 단계 3·5의 자격 경계가 안정되기 전에는 그에 의존하는 작업을 병렬로 구현하지 않는다. 단계 4의 AI 탐지와 단계 3의 서버 연결은 단계 2 이후 파일 소유를 나누어 병행할 수 있다.

단계 7의 소유 경로·버전·복구 계약은 단계 2와 함께 설계하며 첫 배포 전에 기본 갱신/제거 검증을 끝낸다. 단계 5·6은 통합 등록과 자식 프로세스를 추가하는 동시에 해당 정리 절차를 단계 7에 등록해야 완료로 인정한다.

## 7. 계획 검토 기록

2026-10-04 독립 검토에서 짧은 코드의 서버 주소 확보, 관리자 권한 없는 펫에서 외부 AI 자격을 발급받는 승인 흐름, 외부 최초 설치와 운영 서버 자동 업데이트의 범위를 보완했다. 서버 시작의 메인 WebView 의존도 작업에 명시했다. 수정 후 재검토에서 추가 필수 보완 없이 실행 가능한 로드맵으로 판정되었다. 이는 사용자의 구현 승인이나 기능 구현 완료를 뜻하지 않는다.

같은 날 사용자 요청으로 업데이트·제거를 U8–U9와 단계 7로 추가했다. 이 추가분은 문서 자체의 의존 관계·소유 범위·실패 검증 기준을 확인했으며, 앞선 독립 검토 판정이 새 범위까지 검증한 것으로 간주하지 않는다. 실제 업데이트·복구·완전 제거 기능과 설치 검증은 아직 수행하지 않았다.

같은 날 사용자 결정으로 업데이트 실패 복구의 중심 수단을 "프로그램·DB 한 쌍 자동 되돌리기"에서 "글 형식 내보내기 + 복원 전용 가져오기"로 바꿨다(설계 4.7.1). 같은 기능이 임베딩 모델 교체 통로를 겸한다. 이 변경도 독립 검토를 거치지 않았다.

2026-10-06 사용자 결정으로 실행 순서를 1.1절로 확정했다(단계 1 → 4 → 2+7A → 지인 체험 → 7B·7C → 3·5·6 재검토). 계획 작성 뒤 반영된 배포 버전 검사와 글 형식 백업·복원 명령을 단계 7에 표시하고, Review Focus 번호를 바로잡았다.
