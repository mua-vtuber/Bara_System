# 백업 종류 정리 결정 (2026-10-08)

유형: 결정 / 상태: 채택 (일부 구현, 나머지 구현 전)

## 배경

코덱스 조사로 백업이 여섯 종류라는 것이 드러났다. 서버 정기 백업, 대시보드 ZIP, 펫 "백업 만들기",
업데이트 전 백업, 구조 변경 전 사본, 복원 전 보존이다. 코드를 확인해서 아래 사실을 정리했다.

- 펫이 원격·기존 서버에 연결하면 펫 백업 버튼이 꺼지고(`src/ui/settings.ts`), 업데이트 전 백업도
  이 PC의 관리 DB에만 돈다. 그래서 원격 연결 사용자의 PC에는 백업이 하나도 없다.
- 이 PC 모드에서는 모든 백업이 원본과 같은 디스크에 쌓인다. 프로그램이나 사람의 실수는 막지만
  디스크 고장은 못 막는다.
- 스키마가 바뀌는 업데이트에서는 업데이트 전 백업(`backups/pre-update/`)과 구조 변경 전 사본
  (`backups/pre-migration/`)이 같은 시점의 DB를 두 번 복사했다. 조사 당시 코드는 이를 알고 여유 공간을
  두 벌로 계산했다(`src/service/maintenance/upgrade.ts` `assertSpace`).
- 서버 회차 복원 CLI는 현재 DB를 보존하지 않고 덮어썼다. 펫 화면 복원은 원본을 `before-restore-*`로
  옮겨 두는데, 서버 복원만 그러지 않아 둘의 안전 수준이 달랐다.
- 펫 "백업 만들기"와 복원 전 보존 폴더는 자동 정리 규칙이 없다. 사용자만 지운다는 의도된 설계다.

## 결정

| 환경 | 남길 백업 | 변경 |
|---|---|---|
| 서버 (A1 등) | 정기 백업(매일 04:00, 7일), 구조 변경 전 사본(최신 3개) | 회차 복원 전에 현재 파일 보존 — **구현 완료** |
| 펫 · 이 PC 모드 | 정기 백업(로컬 서버), 업데이트 전 백업(최신 2개), "백업 만들기" 버튼 | 업데이트 전 DB 사본의 경로·구조 버전을 확인한 경우 구조 변경 전 사본을 건너뜀 — **구현 완료** |
| 펫 · 원격 모드 | 7일마다 서버 백업을 PC로 받아 둠, 최신 2개 유지 | 새 기능 — **설계 전** |

1. **서버 정기 백업은 유지한다.** 원격 서버와 이 PC 모드의 로컬 서버 모두 지금 기본값을 그대로 쓴다.
2. **구조 변경 전 사본은 서버에서 유지한다.** A1은 `git pull`로 업데이트하므로, 서버의 업데이트 사고를
   막는 유일한 장치다. 자동 기능이다(`apps/memory/src/db/migrations.ts` `openMemoryDatabase`).
3. **업데이트 전 백업은 이 PC 모드에서 유지한다.** 사용자는 "없어도 되지 않나"를 물었으나 유지로 정했다.
   - 펫 복원 화면이 되살릴 수 있는 것은 글 형식 백업("백업 만들기"와 업데이트 전 백업)뿐이다.
     구조 변경 전 사본은 DB 파일이라 화면에서 되살릴 수 없다.
   - 업데이트 전 백업은 스키마가 안 바뀌는 업데이트에도 만들어진다.
4. **중복은 구조 변경 전 사본 쪽에서 줄인다 — 구현 완료.** 펫이 업데이트 전 백업을 확실히 만든 경우에만
   `managed-prepare`에 그 경로를 넘기고, `managed-prepare`가 파일을 확인한 뒤에만 사본을 건너뛴다.
   경로를 넘기지 않으면 지금처럼 사본을 만든다. `assertSpace`도 그때는 DB를 한 번만 계산한다.
5. **"백업 만들기" 버튼은 유지한다.** 문서 폴더에 저장되므로, 이 PC 모드에서 디스크 고장을 견딜
   가능성이 있는 유일한 백업이다(문서 폴더가 OneDrive로 동기화되는 경우).
6. **원격 모드는 서버 백업을 받아 둔다.** 펫이 켜졌을 때 마지막으로 받은 지 7일이 지났으면 받는다.
   최신 2개를 남긴다. 새 백업을 다 받고 검증한 뒤에야 가장 오래된 것을 지운다.

## 검토했으나 택하지 않은 것

- **원격 모드에서 받은 백업을 1개만 남기기:** 서버 데이터가 이미 잘못된 상태에서 받으면 멀쩡한 이전
  사본이 지워진다. 용량이 두 배가 되더라도 2개로 정했다.
- **업데이트 전 백업 없애기:** 위 3번의 이유로 택하지 않았다.
- **이 PC 모드의 로컬 정기 백업 끄기 또는 보관 기간 줄이기:** 논의했으나 사용자가 "서버 정기 백업은 한다"로
  정해 지금 기본값을 유지한다.

## 남은 작업

- 6번 설계. 서버에 첨부까지 담는 내려받기 경로가 없어서(대시보드 ZIP은 첨부·비밀값·토큰 제외)
  새 경로와 소유자 인증 범위를 정해야 한다. 첨부는 내용 해시 이름이라 새로 생긴 것만 받으면 된다.
- 펫 "백업 만들기"와 복원 전 보존 폴더의 용량을 화면에 보이는 일은 아직 정하지 않았다.

## 구현 기록

- 2026-10-08 펫이 `--pre-update-snapshot`으로 넘긴 DB 사본의 절대 경로·관리 루트 내 실제 위치·일반 파일 여부·읽기 전용 구조 버전 일치를 `managed-prepare`가 확인한 때만 중복 사본을 생략한다. 확인 실패 시 stderr에 이유를 남기고 기존 사전 사본을 유지하며, 업데이트 여유 공간에서 중복 DB 한 벌을 뺐다.
- 2026-10-08 서버 회차 복원 전 보존(`apps/memory/src/backup/restore.ts` `preserveRestoreFiles`):
  덮어쓸 DB, `-wal`/`-shm`, 회차에 든 설정·비밀값·토큰을 `<dataDir>/before-restore-YYYYMMDD-HHmmss/`로
  옮긴다. 옮기다 실패하면 제자리로 되돌린다. 옮긴 뒤 단계가 실패하면 오류에 보존 폴더 경로를 붙인다.
