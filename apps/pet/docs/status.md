# 진행 상황

## 별도 사용 안내 창 (2026-10-16, 소스 구현·격리 Windows 검증 완료)

설정창 상단과 트레이 메뉴의 **사용 안내**에서 별도 창을 연다. 기존 메모장 재질·인덱스·창 제어를 재사용하며, 처음 읽기·메모 쓰기·기억 찾기·일정 보기·AI와 연결의 다섯 목차로 구성했다. 답변 AI와 기억 정리 AI의 차이, 평면 태그와 `#상위:하위,` 관계, `#날짜:2026-11-03,` 일정 입력을 실제 구현에 맞춰 설명한다. 서버·AI 연결 없이 읽을 수 있고, 같은 창을 재사용하며 닫기 후에도 페이지·스크롤을 유지한다.

검증: 타입 검사·UI 빌드, 관련 Bun **37 pass / 0 fail**, Rust **143 pass / 0 fail**, `cargo check`·포맷 검사, 독립 코드 검토 통과. 브라우저에서 3개 크기 × 5개 목차의 가로 잘림·하단 탐색·키보드 포커스 확인. 임시 데이터 폴더의 실제 Windows EXE로 설정+안내 동시 표시, 재열기, X/Windows 닫기 후 위치 유지, 최소화 복원, 안내 창의 서비스 접근 거부 등 **7항목** 확인. 운영 데이터는 사용하지 않았으며 설치판 교체·릴리스는 하지 않았다. 엄격 Clippy는 기존 `vault.rs:126`의 `chunks_exact_to_as_chunks` 경고로 실패했고, 해당 경고만 허용한 검사는 통과했다. 실제 모니터 해상도·배율 변경 검증은 하지 않았다.

## 설치 중 잠금 (2026-10-16, 실제 화면 확인 대기)

처음 쓰는 사람이 "이 PC에 준비하기"가 도는 중에 "대시보드 열기"를 눌러 "관리자 인증 링크를 먼저 연결해 주세요."를 본 일이 계기다(관리자 토큰은 설치 맨 끝에 저장된다). 사용자 승인 설계대로 설치가 도는 동안 펫 위에 "설치 중"을 띄우고, 아직 쓸 수 없는 화면으로 넘어가지 않게 했다.

- 서비스: `status` 결과에 `installing`을 더했다. `install.local`·`install.remote`를 받는 순간(연결 대기열에서 차례를 기다리는 동안 포함)부터 성공·실패·중단으로 끝날 때까지 참이며, 세는 곳은 `src/shared/run-count.ts` `RunCount.track` 한 곳이다. 설치 중에는 `dashboard.link`와 `assistant.ask`를 대기열에 넣지 않고 바로 `INSTALL_RUNNING`(문구 `messages.installLock.refused`)으로 거절하고, `memory.save`는 입력을 남기는 거절 결과(`installLock.saveRefused`)로 돌려준다. 트레이 "대시보드"와 메인 창 버튼 모두 이 거절을 받는다.
- 펫: 머리 위 알림 줄에 오래 남는 `install` 알림을 더했다. 모델을 받는 동안은 "설치 중 · 모델 받는 중 2/7 · 42%"처럼 파일 순서와 그 파일의 받은 비율을, 그 밖의 단계는 짧은 단계 이름을 보인다. 창이 열릴 때·다시 보일 때·설치 단계 진행이 올 때 `status`를 묻고, 설치 중에는 2초마다 다시 물어 설치가 끝나면 알림을 지운다. 지나가는 알림(명령 실패·업데이트 등)은 잠시 그 위를 덮고, `listen` 알림보다는 설치 알림이 먼저 보인다(앱을 다시 켜면 설치가 멈추기 때문). 묻기에 실패하면 마지막으로 안 상태를 그대로 두고 원인을 한 번 알린다(설치 중이었다면 알림과 클릭 막기가 유지되고, 모르던 설치를 있다고 가정하지 않는다). 설치 중 펫 클릭은 입력창 대신 "설치가 끝나면 쓸 수 있어요."를 보인다. 설치 알림과 이 안내는 오류가 아니므로 오류 빨강이 아니라 보라 계열(정보) 모양으로 보이고, 명령 실패·계약 위반·듣기 실패·업데이트 실패는 그대로 빨강이다(`noticeLook`). 트레이 "대시보드"가 설치 중이라 거절되면 오류 말풍선을 띄우지 않고 메인 창 상태 줄에만 정보로 알린다(말풍선에는 정보용 종류가 없고, 펫 머리 위 "설치 중"이 이미 보인다).
- 메인 창: 이 창에서 시작한 설치 요청이 도는 동안(`src/ui/install-lock.ts`) 펫 우클릭·트레이 "설정"·메모장 탭·결과 말풍선이 창을 띄우기만 하고 설치 화면을 바꾸지 않아, 진행 표시와 "준비 중단"이 그대로 남는다. 처음 설정에서 시작했다면 저장소 단계에 머물고, "나중에 하기"와 입력·질문 버튼은 설치가 끝날 때까지 기다리라고 안내한다.
- 확인: 새 테스트(실제 `PetService`로 로컬·원격 각각 설치 중 거절과 실패·중단 뒤 해제, 세는 규칙, 펫 알림 규칙, 화면 유지 판단) 포함 펫 전체 139파일 **1154 pass / 0 fail / 56 skip**(이번 마지막 실행은 한 프로세스로 돌려 끝까지 통과했다. 다만 이전에 한 번에 돌리면 Bun 1.3.6 자체가 멈춘 적이 있어 묶음으로 나눠 돌리는 쪽이 안전하다), 타입 검사·UI 빌드 통과. Rust는 바꾸지 않아 `cargo test`는 돌리지 않았다. 실제 앱에서 펫 알림 모양·백분율 갱신·창 유지·트레이 거절은 아직 눈으로 확인하지 않았다. 메인 창을 새로 고친 뒤에는 설치 화면을 다시 붙이지 않는다(서비스 거절만 남음).

## 현재 상태 요약 (2026-10-08)

기준 소스는 `main`의 안정성 수정 `a4579c9a`이며 제품 버전은 **0.1.1**이다. 트레이·펫 숨김과 그리기 중단, 앱 시작·종료 조정, 첫 설치 마법사, AI 탐지·선택, 화면 백업·복원, 업데이트 전 백업이 코드에 반영되어 있다. 커밋 전 시작 화면 수정 `c48b3219`와 함께 네이티브 120개를 재검증했다. 이번 수정의 설치판·운영 서버 배포는 별도다.

- **사용자 확인 완료:** 구버전에서 신버전을 설치한 뒤 기억과 설정이 보존됨(2026-10-08 대화). 정확한 설치 버전 쌍과 파일 해시 비교는 보고되지 않았으므로 자동화된 A→B 전체 검증으로 확대하지 않는다.
- **확인 대기:** 업데이트 뒤 자동 실행 보존(사용자가 기억하지 못함), 실제 화면·트레이에서 백업·복원 중 이동/중단/재실행·종료, 깨끗한 Windows 최초 설치, 여러 모니터·배율. 실제 A→B 실패 복구·제거 검증도 남아 있다. 서비스 수준 자동 검사의 통과와 구분한다.
- **이번 Windows 자동 검사:** 펫 **830 pass / 0 fail / 2 skip**, 네이티브 **118 pass / 0 fail**, 메모리 관련 **59 pass / 0 fail**. 펫·메모리 타입 검사, UI/서비스/네이티브 빌드, Rust 포맷·엄격 Clippy 통과. 이전 실패 30개는 Windows junction fixture와 격리 포트로 해결했다. 실제 AI 분류 평가 2개는 모델 미지정으로 생략했다. [결과와 한계](decisions/2026-10-08-stability-check.md).
- **남은 구현:** 설치기의 낮은 버전 설치 거절·같은 버전 수리·폐기 파일 정리, 두 가지 제거 모드와 소유 경로/외부 등록 정리. 앱의 낮은 버전 **로컬 DB 시작 차단**은 이미 구현되어 있다.
- **보류 유지:** 단계 3(간편 페어링·SSH 자동 준비), 5(외부 AI MCP 자동 등록), 6(Discord 통합 설치·연결). 기존 수동 연결·MCP 서버·독립 봇과 새 자동화 기능을 구분한다.
- **자동 검사에서 수정:** 진행 중인 AI 추출·저장/자동 정리·입력 후처리가 있을 때 초기화가 허용되던 경합, 종료 요청이 끝난 서비스를 다시 띄우던 경합. 기존 쓰기 큐와 DB별 활동 추적을 재사용했다. 백업·복원 중 종료는 실제 서비스/자식 프로세스로 데이터 파일 보존과 프로세스 정리를 확인했다. **다음 확인:** 실제 UI 및 로그오프·재부팅, 전체 설치 검증. 이미지 재계산은 요청 보호만 검사했으며 실제 이미지 모델 배치까지 검사한 것은 아니다.

아래 날짜별 항목은 당시 구현·검증 이력이다. 0.1.0 설치 검증이나 중간 커밋의 검사 통과를 최신 전체 소스의 통과로 간주하지 않는다. 최신 진행 순서는 [실행 계획 1.2–1.3절](decisions/2026-10-04-onboarding-tray-plan.md)을 따른다. 운영 서버 반영은 별도다.

## 진행 방향과 알려진 문제 (2026-10-07)

- 사용자 결정: 당분간 설치판으로 혼자 쓰며 개발한다. 지인 체험은 안전하고 안내문 없이도 쉬운 상태가 된 뒤로 미루고, 화면 백업 내보내기와 7B를 그 전 조건으로 당겼다(실행 계획 1.2절). 쓰면서 생기는 불편은 펫에 `#바라개선` 태그로 기록해 모은다.
- Spine: 사용자는 유료 Spine Editor 라이선스를 갖고 있어 Spine 런타임 쪽 조건은 충족한다(설계 U13, 빌드가 Spine `LICENSE`를 `dist/licenses/`에 넣음). AGPL과의 일관성을 설명하는 추가 허가 문구(설계 O14)는 미정이며, 다른 사람에게 배포하거나 저장소를 공개하기 전에 정한다.
- 저장소 공개: 지금 저장소는 비공개 개발용으로 둔다. 공개할 때는 이력 재작성 대신 정리한 현재 파일로 새 저장소를 만드는 방향을 검토한다. 이력에는 공인 IP·이메일이 든 문서와 예전 `.omx/` 상태 파일이 있으며, 공개 전 사람이 직접 점검해야 한다.
- 메모리 서버 데이터 초기화 누락 수정(2026-10-07): 대시보드 "데이터 초기화"(`apps/memory/src/db/store-internal/stats-repository.ts`)가 이제 정리 작업 표(`cleanup_proposal_item_journal`·`cleanup_stage_results`·`cleanup_runs`)와 사용자 사전(`synonym_user_entries`·`classify_vocab_user_entries`·`classify_vocab_overrides`·`relation_name_user_entries`, `entity_types`의 사용자 추가 종류)을 같은 트랜잭션에서 비운다(사용자 결정: 사전도 지운다). 남기는 것은 `schema_version`·정규식 학습 자산(`regex_user_*`)·`asset_folder_pairing`·`memory_visibility_state`·설정 파일이다. 초기화 뒤 서버의 사전 캐시도 빈 DB에 맞춰 다시 얹으며, 이 갱신이나 첨부 파일 정리가 실패하면 대시보드 상태 줄에 경고로 보인다. 모든 표가 "비움·연쇄 삭제·보존" 중 하나로 분류되었는지 검사하는 테스트를 넣어, 새 표가 생기면 분류하지 않은 채 지나가지 못한다. 확인: 새 테스트 11개 통과, 메모리 타입 검사 통과, 기본 테스트 실패 목록 변경 전과 동일(모델 다운로드가 막힌 환경 탓의 기존 실패). 모델이 필요한 기존 초기화 테스트(`store.test.ts`·`server.test.ts`)는 이 환경에서 실행하지 못했다.
- 백그라운드 작업 중 초기화 차단(2026-10-07, 검토 지적 반영 두 차례): DB에 결과를 쓰는 백그라운드 작업 — 정리(깊은 패스)·추출 백필·이미지 분석 백필 스케줄러, 정기·수동 모두 — 중 하나라도 도는 중에 데이터 초기화를 요청하면 아무것도 지우지 않고 409("백그라운드 작업(정리·추출·이미지 분석)이 진행 중이라 초기화하지 않았다…")로 거절한다. 진행 중이던 작업이 초기화 뒤에 옛 글 번호의 결과를 다시 써서 새 글에 붙는 일을 막는다. 기준은 하나다: 초기화 경로가 `deps.backgroundWritersRunning`(세 스케줄러의 `isRunning` 중 하나라도 참)을 확인하며, `src/index.ts`가 `setBackgroundWritersRunning`으로 얹는다(깊은 패스 전용이던 `cleanupRuns.cycleRunning`은 이 기준으로 합쳤다). 확인과 삭제 사이에 다른 작업이 끼어들 수 없다. 남은 것: 스케줄러가 아닌 비동기 경로 — 즉시 추출(`llm.extractor.mode`가 `immediate`)과 자동 정리 트리거(`src/memory/auto-cleanup-trigger.ts`, 페이지마다 await) — 는 이 확인에 들지 않으며, 초기화와 겹칠 때의 영향은 아직 확인하지 않았다. 확인: 초기화 409 테스트(세 작업 각각 409·끝난 뒤 정상 초기화)·run API·스케줄러 테스트 통과, 타입 검사 통과. `tools-cleanup.int.test.ts`는 모델 다운로드가 막힌 환경이라 실행하지 못했다.

- 메모리 서버 분류 어휘 유실 수정(2026-10-07): 새 엔티티 종류나 관계명을 대시보드에서 추가·삭제하면 `resetConceptTypeVocabularyCache()`가 사용자 분류 어휘를 합친 캐시(병합본·항목 동의어·칸 자료형)까지 비워, 서버를 다시 시작하기 전까지 사용자 분류 어휘가 빠진 기본 어휘로 분류하던 문제를 고쳤다. 이제 그 함수는 파생 캐시만 비우고 주입한 어휘는 남기며(주입분을 버리는 용도는 `clearConceptVocabularyOverrides()`), 종류 추가·삭제 뒤에는 데이터 초기화와 같은 공용 통로(`server-internal/reload-classify-vocab.ts`)로 병합본을 새 종류 목록에 맞춰 다시 얹는다. 후속(같은 날): 분류 어휘·가림표·관계명 행이나 엔티티가 남은 종류는 삭제 요청이 409(남은 항목 이름·개수를 한국어로 안내)로 거절돼 고아가 새로 생기지 않고, 이미 고아가 된 행은 서버 시작·재병합 때 건너뛰며 종류 이름과 개수를 경고로 남긴다(고아 행 하나 때문에 서버가 안 뜨던 문제 해소). 어휘·관계명을 새로 추가할 때의 미등록 종류 거부는 그대로다. 남은 한계: 엔티티를 개별로 지우는 화면·API가 없어, 엔티티가 있는 종류는 그 엔티티를 먼저 정리해야 지울 수 있다. 확인: 새 회귀 테스트(`routes/vocab-cache-preserve.test.ts`) 6개 통과(수정 전 로직에서는 6개 모두 실패), 메모리 타입 검사 통과, 모델이 필요한 라우트 테스트는 모델 로드를 건너뛰어 실행한 결과 변경 전과 동일.

## 백업·되살리기·시작 확인 독립 검토 보완 (2026-10-07, 실제 Windows 확인 대기)

- 되살리기·백업 만들기가 화면이 아닌 서비스의 작업이 됐다(`src/service/background-job.ts` `BackgroundJob`, `SharedRun`과 같은 방식). 예전에는 설정 화면이 사라질 때(`renderBackup` `dispose`) 진행 중인 요청에 `operation.cancel`을 보내, 이미 설정을 보이는 창을 트레이 "설정"·펫 메뉴로 다시 열거나 되살리는 중 저장 거절 말풍선을 눌러 "결과"로 바뀌기만 해도 되살리기가 중단됐다. 이제 작업은 서비스 자신의 신호로 돌고, 요청 취소(화면 떠남·종료 drain)는 그 요청의 기다림만 끝낸다. 작업을 멈추는 것은 화면의 "중단"(새 RPC `backup.cancel { kind }`)과 종료(`service.close`)뿐이고, 멈춘 작업은 `CANCELLED`(문구 `messages.restore.cancelled`, 새 `messages.backup.cancelled`)로 끝난다.
- 다시 붙기: 새 RPC `backup.status`는 종류별로 진행 중인 작업(시작 시각, 마지막 단계와 바이트 진행)이나, 기다리던 화면이 없어 아직 아무도 받지 못한 끝난 결과(완료·실패·중단)를 한 번 돌려준다. `backup.join { kind }`은 진행 중인 작업에 합류해 마지막 단계를 먼저 다시 받고 끝까지 진행·결과를 받는다(끝났으면 그 결과). 설정 화면은 열릴 때 `backup.status`를 읽어 진행 중이면 합류해 단계 문구·지난 시간(서비스의 시작 시각 기준)·"중단"을 보이고(되살리기면 목록을 꺼진 채 펼침), 끝난 결과가 있으면 상태 줄에 보인다(`src/ui/backup-jobs.ts` `JobFollower`). 화면이 떠날 때는 자기 기다림 요청만 `operation.cancel`한다. 세 메서드는 메인 창만 보낼 수 있다(`policy.rs`), `backup.join`은 상한 없음.
- 같은 화면 유지: 메인 창은 이미 설정(또는 처음 설정)을 보이는 중에 호스트가 같은 화면으로 `pet-panel`을 보내면 다시 그리지 않는다(`src/ui/panel-view.ts`). "결과"·"마지막 답"은 예전처럼 매번 새로 그린다.
- 되살리기의 서버 멈춤을 맨 앞으로: 이전에는 백업 확인(verify)·공간 확인·모델 받기(몇 분 걸릴 수 있음)가 끝난 뒤에야 서버를 멈춰, 그동안의 저장이 성공으로 답한 뒤 `before-restore-*`에만 남았다. 이제 되살리기가 시작되는 순간부터(목록에서 백업을 찾은 직후, 작업 시작과 같은 때) `restore.active`·`holdingServer`가 켜져 저장은 기존 거절 문구(`messages.restore.saveRefused`)로, 서버가 필요한 다른 요청은 `RESTORE_RUNNING`으로 바로 거절되고(`router.ts`, 서버를 멈추기 전에도), 같은 연결 대기열 경로로 곧바로 서버를 멈춘 뒤 확인을 시작한다. 교체 전 어떤 실패·중단이든 서버를 예전처럼 다시 시작한다.
- 종료 중 재시작 금지: `service.drain`이 시작되면 맨 먼저 `PetService.beginDrain`으로 되살리기에 종료를 알려, 그 뒤 끝나는 되살리기는 서버를 다시 시작하지 않는다(관리 준비·7B 게이트 포함 아무것도 시작하지 않음). `close`는 재시작 금지 표시 → 진행 중 작업 중단 → 최대 2초 정리 대기 → 로컬 서버·터널 종료 순이다.
- 기록: 교체 기록이 `restoring`인 채 교체 전에 끝난 실행(예: 교체 계획을 위한 드라이브 읽기, 교체 첫 기록 쓰기 실패)은 이제 서버를 다시 시작하기 전에 `failed`(오류 코드 포함, 중단이면 `cancelled`)로 기록한다. `interrupted`는 시작 때 발견한 진짜 끊김에만 남아, 화면이 "끝나기 전에 바라가 종료" 줄을 잘못 보이지 않는다.
- 시작 확인 보고 한 번: 호스트는 확인이 끝나면 결과와 무관하게 보고를 마감한다(`startup.rs` `settle_for_host`). 메인 창이 먼저 맡았으면 "보고함"으로 바뀌어, 확인이 끝난 뒤 다시 로드된 메인 페이지(새로 고침, WebView2 충돌 복구)는 `claim_startup_report`에서 거짓을 받아 실패 말풍선을 다시 내지 않고 상태 줄만 갱신한다. 확인이 진행 중일 때 다시 로드된 페이지는 여전히 보고를 맡는다.
- 펫 표시 동기화 실패는 시작을 막지 않는다: `tray::set_pet_visible`이 한 단계(WebView 표시·창 표시·`pet-visibility` 이벤트)가 실패해도 나머지 단계를 모두 시도하고 첫 실패를 돌려주며(창 상태는 항상 적용), 앱 시작(`setup`)은 그 실패를 무시한다(펫 페이지는 로드 때 `get_pet_visible`로 상태를 다시 묻는다). 트레이 토글·마법사는 예전처럼 실패를 알린다.
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드. 새 테스트 — 서비스 되살리기 5개(요청이 떠나도 계속되고 합류하면 단계 재전송과 결과, 아무도 받지 못한 결과는 다음 `status`에 한 번, 시작부터 저장 거절·verify 전에 서버 멈춤·이전 폴더에는 시작 전 저장소만, 종료 중 실패해도 서버를 시작하지 않음, 교체 첫 기록 실패가 `interrupted`가 아닌 `failed`), 백업 1개(화면이 떠나도 계속·합류·종료로 중단), 서비스 전체 1개(verify 중 저장 거절과 `status`, 화면이 떠난 뒤 `backup.status`·`backup.join`·`backup.cancel`, 메모리 보관소에서만 실행됨), 화면 따라가기 5개(떠날 때 `backup.cancel`을 보내지 않음, 다시 열면 단계·시간·결과, 끝난 결과 표시, "중단", 표시 순서), 같은 화면 유지 1개. 기존 테스트는 중단을 `operation.cancel` 대신 `backup.cancel`로 하도록, verify·공간·모델 실패는 서버가 멈췄다가 다시 시작되도록 기대값을 바꿨다. UI·서비스 테스트 525 pass / 4 fail(변경 전 513/4, 같은 리눅스 전용 목록), 펫 전체 756 pass / 6 fail(임시 메모리 보관소, 변경 전 743/6, 같은 리눅스 전용 목록). Rust 포맷·Windows 대상 엄격 Clippy(`--tests`)·테스트 94개(새 테스트: 세 메서드는 메인 창만, 확인이 끝난 뒤 다시 로드된 페이지는 보고하지 않음, 표시 단계 실패에도 모든 단계 시도).
- Windows에서 확인할 것: (1) 되살리는 중 트레이 "설정"·펫 메뉴의 설정으로 창을 다시 열어도 진행이 그대로인지, 저장 거절 말풍선을 눌러 "결과"로 갔다가 설정으로 돌아오면 단계·지난 시간·"중단"이 다시 보이고 끝나면 결과 줄이 뜨는지. (2) 같은 방법으로 백업 만들기가 계속되는지. (3) 모델을 받는 동안(캐시를 지운 상태) 펫에 입력하면 "저장하지 않았어요…" 말풍선이 뜨는지. (4) 되살리는 중 "바라 종료" 뒤 작업 관리자에 메모리 서버가 남지 않는지. (5) 시작 실패 상태에서 메인 창 개발자 도구로 페이지를 새로 고쳐도 실패 말풍선이 다시 뜨지 않는지.

## 화면에서 백업 되살리기 (2026-10-07, 실제 Windows 확인 대기)

- 연결과 설정의 "백업" 칸에 "백업에서 되살리기"를 넣었다(`src/ui/settings.ts` `renderBackup`, 문구 `src/ui/restore-model.ts`·`messages.restore`). 목록 → 고르기 → 확인 대화상자(지금 기억은 "복원 전" 폴더로 옮겨 남김, 끝날 때까지 서버가 멈춤, 색인 재계산으로 오래 걸릴 수 있고 모델이 없으면 내려받음, 설정·로그인은 그대로) → 진행(단계 문구는 `role=status` 줄, 지난 시간은 따로 매초 갱신, "중단"은 기억을 바꾸는 단계 전까지만. 화면을 떠나도 계속되며 다시 열면 이어서 보인다 — 위 "독립 검토 보완") → 결과 줄 "되살렸어요: 기억 N개·첨부 M개. 되살리기 전의 기억은 이 폴더에 그대로 있어요: …" 또는 오류. 원격·기존 서버 연결이면 버튼이 꺼지고 이유를 보인다. 목록 위에 지난 되살리기의 결과(완료와 이전 데이터 위치, 시작 전 끊겨 되돌림, 중간에 종료됨)를 보인다.
- 목록(`backup.list`, `src/service/restore.ts`): 호스트 백업 폴더의 `bara-backup-*`(`manifest.json`)와 `<데이터>\memory\backups\pre-update\*`(`update-backup.json`과 `portable\manifest.json`). 링크·이름이 다른 폴더·기록을 읽을 수 없는 폴더는 뺀다. 최신순 100개. 항목은 종류·이름·날짜·기억·첨부 수와 불투명한 id(종류+폴더 이름의 해시)만 갖고 경로는 화면에 가지 않는다. `backup.restore { id }`는 서비스가 새로 목록을 읽어 id로 찾는다. 두 메서드는 메인 창만 보낼 수 있다(`policy.rs`).
- 순서와 안전장치: (1) 완료된 로컬 설치만(`RESTORE_NOT_LOCAL`/`RESTORE_NOT_READY`, 설정의 DB가 관리 DB가 아니면 `RESTORE_SETTINGS_INVALID`). 업데이트 마무리 중(`UpdateGate.busy`), 설정 백업 중, 연결 작업·시작 확인 중이면 거절하고(`RESTORE_UPDATE_RUNNING`/`RESTORE_BACKUP_RUNNING`/`RESTORE_CONNECTION_BUSY`), 반대로 되살리는 중에는 설정 백업(`BACKUP_RESTORE_RUNNING`)과 연결 변경·설치(`RESTORE_CONNECTION_LOCKED`, AI·자동 실행 저장은 가능)를 거절한다. (2) `portable-memory.ts verify --archive`로 다시 읽어 통과해야 다음으로 간다. (3) 여유 공간: 백업 폴더 크기(첨부 포함) + 색인 행당 여유분(글 벡터 bge-m3 1024×4바이트, 이미지·개념 이름 벡터 SigLIP 768×4바이트, 각각 sqlite-vec 청크·행 지도와 FTS·트라이그램 색인 몫으로 두 배 — `TEXT_INDEX_ALLOWANCE`·`IMAGE_INDEX_ALLOWANCE`, 대상 컬렉션은 `restore-indexes.ts`와 같음)을 두 번(복원이 작업 폴더에 만든 뒤 옆에 복사본을 게시하고 첫 것을 지움) + 200MB. 이어서 되살리기는 이미 쓴 작업 폴더 크기를 빼고, 새로 시작하면 지울 작업 폴더 크기를 여유에 더한다. 읽지 못하면 진행. 실측은 모델이 없어 하지 못했다. (4) 모델: 설치와 같은 `prefetch-core-models.ts`를 같은 모델 폴더 환경(`BARA_HF_CACHE_DIR`=`memory\models\hf-cache`, `BARA_KIWI_MODEL_DIR`, `managed-prepare`와 같은 계산, 실행하지는 않음)으로 돌려 받기·확인하고 바이트 진행률을 보인다. 여기까지 저장소는 아무것도 바뀌지 않는다. 서버는 (2)보다 먼저, 되살리기 시작 때 이미 멈춰 있다(아래).
- 서버 멈춤 시점(결정): 되살리기를 시작할 때, 백업 확인·공간 확인·모델 받기보다 먼저 멈춘다(2026-10-07 독립 검토 보완 전에는 모델 받기 뒤였다). 되살리는 중 서버가 받은 저장은 곧 옆으로 옮겨질 저장소에 들어가 교체 뒤 조용히 사라지기 때문이다. 시작 순간부터 저장과 서버가 필요한 요청을 라우터에서 거절하고, 연결 대기열 안에서 멈춰(이미 진행 중인 요청은 먼저 끝남) 끝날 때까지 로컬 서버 시작을 시작 게이트에서 `RESTORE_RUNNING`으로 거절한다. 그래서 입력은 바로 `rejected`("…저장하지 않았어요. 입력한 내용은 입력창에 그대로 남아 있어요…")로 답해 입력창에 글이 남고, 질문·연결 확인은 이유를 말하며, `status`는 "…서버를 멈춰 두었어요"를 보인다. 대기열을 복원 내내 잡지 않으므로 기다리다 15분 상한에 걸리지 않는다.
- 복원: `portable-memory.ts restore --archive <백업> --out <데이터>\memory\restore-work\target --model bge-m3 --resume`(항상 `--resume`: 이어 갈 것이 없으면 새로 시작). 저장소와 같은 드라이브라 교체가 이름 바꾸기다. 출력이 끊긴 채 30분이면 멈춘 것으로 본다(`RESTORE_IDLE_MS`, 복원은 8개 단위마다 진행 줄을 쓴다). 총 상한은 없고(`operation-limits.ts`) 화면의 중단이 끝낸다. 중단·실패면 기록에 남기고 지금 저장소는 손대지 않은 채 서버를 다시 시작하며, 작업 폴더(`job.json`에 백업 id·fingerprint·앱 버전)를 남겨 같은 백업을 다시 고르면 "이어서 되살리기"로 보이고 이어 간다. 다른 백업·바뀐 백업 내용·다른 앱 버전이면 작업 폴더를 지우고 새로 한다. 끝나면 복원 보고의 기억·보관함 수와 영수증의 첨부 수를 백업 manifest(verify가 읽은 것)와 대조하고 다르면 바꾸지 않는다(`RESTORE_COUNT_MISMATCH`).
- 교체 기록 `<데이터>\restore-state.json`(`src/service/restore-journal.ts`, 임시 파일에 쓰고 디스크에 flush한 뒤 이름 바꾸기): `restoring` → `swapping`(이동 목록 전체를 먼저 기록) → `swapped` → `complete`(서버가 되살린 저장소로 시작), 실패 쪽은 `rolling-back` → `rolled-back`, 끝난 표시로 `interrupted`·`cancelled`·`failed`(교체 전에 끝난 실행은 서버 재시작 전에 `failed`·`cancelled`로 남기고, `interrupted`는 시작 때 발견한 끊김에만 쓴다). 이동: 지금 `db\bara.sqlite`와 있는 동반 파일(`-wal`·`-shm`·`-journal`), `assets` 폴더 전체를 `memory\before-restore-YYYYMMDD-HHmmss\{db,assets}`로, 그다음 되살린 `memory.sqlite`를 `db\bara.sqlite`로, 되살린 `assets` 폴더 전체를 `assets`로(새 짝 표시 파일과 DB의 `asset_folder_pairing`이 같은 번호라 메모리 서버의 시작 규칙 `decideAssetFolderPairing`이 "진행"으로 판정 — 실제로 되살린 파일로 확인). 이동 뒤 DB의 sha256·크기, 짝 표시 파일, 첨부 파일 수·바이트를 영수증과 대조하고, 그 기록(`swapped`)을 쓴 뒤에만 서버를 시작한다. 이동 실패·대조 실패는 거꾸로 되돌리고(`RESTORE_SWITCH_FAILED`, 서버 재시작, 되살린 사본은 작업 폴더로 돌아가 다음 시도가 바로 이어짐), 되돌리기마저 실패하면 기록을 `rolling-back`으로 두고 서버를 시작하지 않는다(`RESTORE_ROLLBACK_FAILED`). Windows 잠금(EPERM·EBUSY·EACCES)은 이동마다 약 16초 동안 다시 시도한다.
- 복구 규칙: 매 로컬 서버 시작이 DB를 보기 전에(`StartGate.beforeStart`: `ensureConnection`의 설치 데이터 확인 전, `install.local` 시작) 그리고 서비스 시작 때 한 번(`main.ts`, `maintenance.json`의 "데이터 있음" 판정 전) 기록을 읽는다. `restoring`이면 저장소가 그대로라 `interrupted`로 표시하고 시작, `swapping`이면 남은 이동을 마저 하고 대조(실패하면 되돌림), `rolling-back`이면 계속 되돌림, `swapped`면 할 일 없음(시작 뒤 `complete`). 어떤 이동이 끝났는지는 디스크 상태로, 무엇이든 옮기기 전에 계획 전체를 판정한다: 받는 쪽이 있으면 끝난 이동(보내는 쪽도 있으면 뒤 이동이 같은 자리를 채운 경우만 허용), 보내는 쪽만 있으면 남은 이동, 그 밖은 아무것도 옮기지 않고 멈춘다. 덮어쓰거나 지우는 일이 없어 원래 데이터를 잃지 않고, 두 번 해도 한 번과 같다. 끝내지도 되돌리지도 못하면 `RESTORE_RECOVERY_FAILED`(이전 폴더 경로 포함)로 시작을 거절한다 — 그대로 시작하면 `managed-prepare`가 빈 DB를 만들 수 있기 때문이다. 기록의 경로가 관리 `memory` 폴더 밖이면 기록을 무시한다.
- 교체 뒤: 서버를 일반 연결 경로(`ensureConnection` → 시작 게이트 → `managed-prepare` → 시작)로 시작하고, 결과로 되살린 기억·보관함·첨부 수(백업 manifest와 대조한 값)와 이전 데이터 위치를 돌려준다. 시작이 실패하면 교체는 유지하고 `RESTORE_START_FAILED`(이전 폴더 경로)로 알리며 다음 시작이 `complete`로 마무리한다. 이전 폴더는 자동으로 지우지 않는다. 설정·토큰·AI 키·초안은 건드리지 않는다.
- 함께 고친 것: 글 형식 명령의 결과 줄(manifest에 첨부 목록 포함)이 `runCaptured`의 1MB 출력 한도를 넘을 수 있어(첨부 약 5천 개 이상) 내보내기·업데이트 전 검증·되살리기의 stdout 한도를 64MiB로 올렸다(`PORTABLE_RESULT_MAX_BYTES`). 업데이트 실패 문구가 백업에서 되살리기로 업데이트 전 백업을 고르도록 안내한다.

## 단계 1C② 앱 시작 때 서버 시작·연결 확인 (2026-10-07, 실제 Windows 확인 대기)

- 이전: 메모리 서비스(Bun) 자체가 첫 요청 때 뜨고, 앱 시작 때 그 첫 요청은 메인 창 페이지의 시작 확인(`settings.get` → `connection.test`)이었다. 그래서 메인 창 페이지가 로드되지 않으면(자원 오류 등) 로컬 메모리 서버·SSH 터널·기존 서버 확인과 7B 업데이트 전 백업이 시작되지 않았고, 시작 실패 말풍선도 없었다. 서버는 사용자가 펫에 처음 저장하거나 질문할 때(그 요청의 `ensureConnection`) 비로소 시작됐다(MCP 등 외부 연결은 그때까지 서버 없음).
- 이제 호스트가 앱 시작 직후(트레이 생성·펫 표시 적용 뒤, 펫을 보이든 트레이로만 시작하든) 서비스에 새 요청 `startup.check`를 보낸다(`src-tauri/src/startup.rs`). 서비스는 이 확인을 실행마다 한 번만 돌리고(`src/service/shared-run.ts` `SharedRun`), 나중에 온 요청(메인 창)은 같은 실행에 합류해 같은 결과를 받는다. 확인 내용은 화면이 하던 것 그대로다: 설정 읽기 → 토큰이 있으면 `connection.test`와 같은 연결 대기열·`ensureConnection` 규칙(`router.ts` `startupCheck`, 함수 `checkStartup` 재사용). 설치를 하지 않으므로 완료되지 않은 로컬 설치는 준비하지 않고, 완료 기록이 있는데 DB가 없으면 `INSTALL_DATA_MISSING`으로 멈춘다(새 빈 DB를 만들지 않음). 연결 부분은 `connection.test`와 같은 15분 상한을 확인 자체의 신호로 갖고, 각 요청의 기다림에는 상한을 따로 두지 않는다. 요청 하나가 취소돼도 확인은 계속되며 종료(`service.drain`)만 멈춘다.
- 진행 단계는 기다리는 모든 요청에 각자의 요청 ID로 전달되고, 확인 중에 합류한 요청은 마지막 단계를 먼저 한 번 받는다. 그래서 늦게 열린 메인 창도 "업데이트 전에 기억을 백업하는 중이에요…"를 상태 줄·말풍선으로 보인다. 끝난 뒤 합류하면 다시 보내지 않는다.
- 결과 표시는 한 번만 한다. 메인 창이 로드되면 먼저 새 명령 `claim_startup_report`로 보고를 맡고, 맡으면 예전과 똑같이 상태 줄·백업 말풍선·실패 말풍선(`background`)을 낸다. 확인이 끝날 때까지 메인 창이 맡지 않으면 호스트가 실패만 직접 보인다: 서비스가 함께 보낸 같은 실패 말풍선(화면과 같은 문구, 호스트가 검사·가림 처리하고 `background`로 고정)을, 요청 자체가 실패하면(서비스 시작 실패 등) 새 호스트 알림 `HOST_STARTUP_CHECK_FAILED`를 보인다. 펫을 숨긴 동안에는 기존처럼 "최근 결과"에 두고 트레이를 "확인할 결과 있음"으로 바꾼다. 확인이 이미 끝난 뒤 메인 창이 열리면(처음 로드든 다시 로드든) 상태 줄만 갱신한다. 종료 중이면 아무것도 보이지 않는다.
- 메인 창의 요청 자체가 실패하면(서비스가 응답하지 않음 등) 연결 확인 실패로 본다(예전에는 첫 요청이 `settings.get`이라 설정 읽기 실패 문구였다).
- 자동 실행 되살리기는 그대로 메인 창이 확인이 끝난 뒤 한 번 한다(호스트는 하지 않음). 메인 창이 로드되지 않으면 이번 실행에는 하지 않는다.
- 웹뷰 중 `startup.check`를 보낼 수 있는 것은 메인 창뿐이다(`policy.rs`).
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, 새 테스트 — 공유 실행(합류·진행 전달과 재전송·한 요청 취소·종료·실패) 5개, 화면 관찰 3개, 실제 서비스 프로세스로 호스트·화면 요청이 서버 확인 1회를 함께 받음·실패 말풍선 동봉·확인 중 종료(두 요청 모두 취소 응답, drain 응답)·준비 안 된 로컬 설치에서 DB를 만들지 않음 4개, 상한 정책 1개. UI·서비스 테스트 476 pass / 3 fail, 펫 전체 704 pass / 6 fail(임시 메모리 보관소, 두 경우 모두 변경 전과 같은 리눅스 전용 실패 목록). Rust 포맷·Windows 대상 엄격 Clippy(`--tests`)·테스트 90개(새 테스트 5개: 보고 맡기, 결과별 표시, 종료 중 무표시, 메인 창 전용 허용).
- Windows에서 확인할 것: (1) 펫을 보이는 상태와 트레이로만 둔 상태 각각으로 다시 실행했을 때 메인 창을 열지 않아도 로컬 메모리 서버가 뜨는지(작업 관리자, 또는 대시보드가 바로 열리는지). (2) 서버 연결 실패 상태(예: 기존 서버 주소를 끈 상태)로 시작할 때 펫이 보이면 실패 말풍선이 한 번만, 숨겼으면 트레이가 "확인할 결과 있음"이 되고 "최근 결과"에 그 문구가 있는지. (3) 7B 업데이트 시작에서 백업 진행 문구·말풍선이 예전처럼 한 번 나오고 끝나면 내려가는지, 자동 실행 되살리기가 한 번만 되는지. (4) 시작 확인 중 트레이 "바라 종료"가 20초 안에 끝나고 말풍선이 뜨지 않는지. (5) 첫 실행(연결 정보 없음)에서 마법사가 예전처럼 열리는지.

## 단계 1C① 숨긴 펫 그리기 중단 (2026-10-07, 실제 Windows 확인 대기)

- 원인: Tauri의 창 숨김(`hide()`)은 창만 숨기고 WebView2의 `IsVisible`은 그대로 둔다(tauri-runtime-wry·wry 소스 확인). 그래서 숨긴 펫 창의 페이지는 계속 `document.visibilityState === "visible"`이었고, 그것만 보던 프레임 루프가 숨긴 동안에도 돌 수 있었다(Spine 설계 6.8·O15).
- 호스트: 펫을 보이거나 숨기는 길을 `tray::set_pet_visible` 하나로 모았다. 숨길 때는 창 → WebView(`IsVisible` 끔) 순, 보일 때는 WebView → 창 순으로 바꾸고, 펫 창에 새 이벤트 `contract.petVisibilityEvent`(`pet-visibility`, 값 `true`/`false`)를 보낸다. 트레이 토글·마법사의 표시 방식(`apply_display_mode`)·앱 시작(트레이로만 시작할 때도)·펫 창 Alt+F4(`hide_pet_on_close`, 예전처럼 이번 실행에만 숨기고 저장하지 않으며 트레이 토글 이름도 맞춘다)가 이 함수를 쓴다. 한 단계가 실패해도 나머지 단계를 시도하며, 앱 시작에서는 실패를 무시해 시작을 막지 않는다(독립 검토 보완). 페이지가 로드 때 묻는 새 명령 `get_pet_visible`은 펫 창만 부를 수 있다.
- 화면: 펫 창은 이벤트를 먼저 듣고 나서 `get_pet_visible`을 묻는다. 질문 중에 온 이벤트가 더 새 값이므로 그때의 답은 버린다. 질문이 실패하면 아무것도 모를 때만 보임으로 본다(숨긴 WebView는 페이지 자체가 숨김이라 그래도 그리지 않는다). 호스트 신호와 `document.visibilityState`가 모두 보임일 때만 그린다(`pet-presence.ts`).
- 지연 생성: 펫이 처음 보일 때에야 Spine 런타임 모듈을 불러오고 WebGL 문맥·그림 파일을 만든다. 트레이로만 시작하면 "펫 보이기" 전까지 만들지 않는다. 그동안 온 결과·작업 알림은 쌓아 두었다가 생성 뒤 넘기며, 며칠 숨겨 두어도 커지지 않도록 최대 64개(기억하는 결과 ID 32개의 두 배)만 남긴다. 끝난 작업부터 버리고 아직 진행 중인 작업은 남겨, 처음 보일 때 생각 중 동작이 맞게 나온다. 동작 줄이기 설정은 생성 때 다시 읽는다. 처음 보일 때 시작 연출이 나오는 것은 처음 보는 것이므로 의도한 동작이다.
- 숨김·재표시: 숨기면 `requestAnimationFrame` 요청을 취소하고 다시 요청하지 않는다(프레임·Spine 갱신·그리기 0, 렌더러 소유 타이머 없음). 다시 보이면 첫 프레임의 경과 시간을 0으로 두어 숨긴 시간이 움직임 시계와 Spine 재생에 더해지지 않고, 이후 프레임도 기존처럼 0.1초로 자른다(`frame-loop.ts` `setVisible`·`frameDelta`). 입력창·말풍선·메인 창은 별도 창이라 영향이 없고, 펫 창의 클릭·끌기·오른쪽 클릭과 알림 줄도 캐릭터 생성과 무관하게 동작한다.

## 설정 창 위치: 펫·트레이 근처에 열기 (2026-10-07, 실제 Windows 확인 대기)

## 단계 7B 업데이트 전 자동 백업 (2026-10-07, 실제 Windows 확인 대기)

- 새 버전이 이 PC의 기억 DB를 처음 열기 전에(`managed-prepare`가 마이그레이션하기 전) DB 스냅샷(`apps/memory/scripts/db-snapshot.ts`, 읽기 전용 `VACUUM INTO` + `integrity_check`)과 글 형식 내보내기를 만들고, 내보낸 것을 `portable:verify`로 다시 읽어 개수를 맞춘 뒤에만 진행한다(`src/service/maintenance/upgrade.ts`). 위치는 `<데이터>\memory\backups\pre-update\<이전>-to-<새>-YYYYMMDD-HHmmss`(`bara.sqlite`, `portable\`, 마지막에 쓰는 `update-backup.json`), 완성된 것 최근 2개만 남기되, `update-state.json`이 가리키는 백업은 오래되어도 지우지 않는다. 시작 전 여유 공간(DB+WAL 두 벌 — 업데이트 전 스냅샷과 글 형식 내보내기 예상량 — +첨부·설정 등+200MB)을 확인한다. 확인된 업데이트 전 사본이 있으면 `managed-prepare`의 중복 사본 몫은 따로 잡지 않는다.
- 대상: 이 PC 설치에서 `update`이거나, 기록이 없는데 DB가 이미 있는 `first-run`(기록 이전 설치). 이때 `maintenance.json`의 새 버전은 시작할 때가 아니라 서버가 실제로 뜬 뒤 기록한다(`completeUpdate`). 이 PC에 관리 DB가 없으면(원격·기존 서버 연결, 아직 설치 전) 지킬 데이터가 없으므로 새 버전을 시작할 때 바로 기록한다. `downgrade`, `unreadable`(이 앱이 모르는 형식의 JSON 객체, 더 새 앱의 기록일 수 있음)이면 DB를 열지 않고 `UPDATE_VERSION_UNSAFE`로 멈춘다. `read-failed`(파일이 잠깐 잠김 등)면 다음 시도(연결 확인 등)가 기록을 다시 읽어 그 내용대로 판단하므로 앱을 다시 켜지 않아도 되고, 계속 못 읽을 때만 멈춘다. 깨진 기록(JSON이 아님, 빈 파일, 객체가 아님 — 매 시작마다 다시 쓰는 파일이 정전으로 0으로 채워진 경우 등)은 기록 없음으로 본다: 관리 DB가 있으면 `first-run`이라 백업부터 하고(백업은 읽기만 하며, `managed-prepare`는 더 새 앱이 만든 DB를 아무것도 쓰기 전에 `SchemaVersionTooNewError`로 거절한다 — `apps/memory/src/db/migrations.ts` `openMemoryDatabase`가 버전 판정을 가장 먼저 한다), 서버가 뜬 뒤 올바른 기록을 다시 쓴다.
- `update-state.json`이 단계(`backup`→`backed-up`→`migrating`→`complete`, 실패 시 `failed`)를 남긴다. 백업 중 끊기면 다음 시작이 남은 폴더를 지우고 다시 만든다. 백업이 실패했는데 폴더를 지우지 못하면(Windows에서 파일이 열려 있음) 그 경로를 실패 기록에 남겨 다음 실행이 지우며, 고른 이름에 그 사이 다른 폴더가 생겨 만들기에 실패하면 그 폴더는 건드리지 않는다. `migrating` 이후에 끊기거나 실패하면 DB가 이미 바뀌었을 수 있어 새 "업데이트 전" 백업을 만들지 않고 처음 백업을 알린다. 그 사이 다른 대상 버전(예: 실패한 1.1 위에 고친 1.1.1)을 설치해도 같으며, 기록의 대상 버전만 새 버전으로 바꾸고 처음 백업 경로를 그대로 둔다. 다른 버전이 그 사이 데이터를 썼으면(`maintenance.json` 시각이 다름) 새로 백업한다. `status.update`로 알리며, 이 PC 저장소에 연결된 설정 화면에만 끝나지 않은 업데이트 줄을 보인다(다른 연결이면 숨기고, 이 PC를 다시 고르면 보인다). 버전 기록이 이미 그 대상 버전이고 진행 중인 업데이트가 없으면(`complete` 저장 직전에 앱이 끝난 경우) 끝난 업데이트로 보고 줄을 보이지 않는다.
- 백업 뒤 실패는 `UPDATE_START_FAILED`로 원인과 백업 폴더를 함께 알린다. 화면에서 되살리기는 아래 "화면에서 백업 되살리기"(2026-10-07)로 반영했고, 이 문구가 그쪽으로 안내한다. 진행 중에는 시작 확인과 설정 화면에 "업데이트 전에 기억을 백업하는 중이에요…"를 보이고, 시작 확인 중이면 말풍선도 띄운다.
- 업데이트 전 백업이 도는 동안과, 업데이트로 시작한 서버 시작이 끝나기 전(`managed-prepare`가 마이그레이션 중일 수 있음)에는 설정 화면의 백업 내보내기를 `BACKUP_UPDATE_RUNNING`("업데이트를 마무리하는 중이라 백업하지 않았어요…")으로 거절한다(`UpdateGate.busy`). 시작이 취소되면 게이트가 듣고(`StartGate.cancelled`) 풀린다.
- 백업은 요청과 따로 돈다: 요청의 15분 제한이나 취소는 그 요청의 기다림만 끝내고, 다음 요청이 같은 백업에 합류한다. 종료(drain)만 백업을 멈추고 이번 폴더를 지운다. 단계별 제한은 스냅샷·검증 30분, 내보내기 60분.
- `managed-prepare`는 기본적으로 메모리 서버와 같은 사전 스냅샷(`<backup.dir>\pre-migration`)을 켜고 DB를 연다. 펫이 업데이트 전 DB 사본을 `--pre-update-snapshot`으로 넘겼을 때만 절대 경로·관리 루트 내 실제 위치·링크가 아닌 일반 파일 여부를 확인하고, 사본과 현재 DB를 읽기 전용으로 열어 `schema_version` 최고값이 같으면 사전 스냅샷을 생략한다. 경로가 사라졌거나 구조 버전이 다른 등 검증이 실패하면 stderr에 이유를 남기고 기존 사전 스냅샷을 만든다(2026-10-08 구현 완료, `decisions/2026-10-08-backup-policy.md`). 인자가 없는 실행과 메모리 서버의 정책은 그대로다. 스키마를 바꿀 때는 새 내보내기가 직전 배포의 스키마를 읽을 수 있어야 한다(`apps/memory/README.md`).
- 업데이트 뒤 자동 실행 되살리기(2026-10-07): 새 버전 설치 프로그램의 기본 선택("설치 전에 제거")은 이전 버전의 제거 프로그램을 `/UPDATE` 없이 실행하고, 그 제거 훅이 HKCU `Run`의 `BaraPet` 값을 지워 업데이트 뒤 "Windows에 로그인하면 바라를 함께 켜기"가 꺼져 보였다. 이미 설치된 이전 제거 프로그램은 고칠 수 없으므로 앱이 되살린다: 시작 확인이 끝난 뒤(성공·실패 무관) 화면이 한 번 `status`의 `maintenance.run`과 저장된 `settings.autoStart`를 읽고, 실행 종류가 `update` 또는 `first-run`(저장값이 켜짐이면 이전 버전이 이 PC에서 돌았다는 뜻, 기록 이전 버전에서의 업데이트)이고 저장값이 켜짐이며 `Run` 값이 아예 없을 때만(새 호스트 명령 `has_autostart_entry`) 설정 화면과 같은 `set_autostart(true)`로 현재 실행 파일을 다시 등록한다(`src/ui/autostart-restore.ts`). 값이 있으면(다른 경로를 가리켜도, 작업 관리자가 `StartupApproved`로 꺼 둔 경우도) 건드리지 않고, 저장값이 꺼짐이면 켜지 않으며, 읽기·쓰기가 실패해도 시작을 막지 않고 다시 시도하지 않는다(설정 화면은 레지스트리의 실제 상태를 보인다). `same-version`은 일반 재시작과 구별되지 않아 제외했다(같은 버전 재설치의 "제거"는 기본 선택이 아님). 설정 화면의 토글은 이미 레지스트리와 `settings.autoStart`를 함께 쓰고 저장 실패 시 되돌린다. NSIS 제거 훅은 Tauri 템플릿(tauri-cli 2.11.4)이 자기 `Run` 항목에 쓰는 `${If} $UpdateMode <> 1`과 같은 조건으로 바꿨지만, 그 템플릿은 이전 제거 프로그램에 `/UPDATE`를 실제로 넘기는 경로가 없어 지금은 관례를 따르는 것일 뿐이고 보존은 앱의 되살리기가 맡는다. 확인(Linux): 타입 검사, UI·서비스 빌드, 결정 함수 테스트 7개, 펫 전체 674 pass / 리눅스 전용 6 fail(변경 전과 같은 목록), Rust 포맷·Windows 대상 엄격 Clippy(새 Windows 전용 테스트 포함 컴파일)·테스트 76개. 실제 Windows에서 A→B 업데이트 뒤 등록이 돌아오는지는 확인하지 않았다.
- 남은 것: 모델 교체 흐름, 격리 환경의 실제 A→B 전체 검증(7D, 자동 실행 되살리기·실패 복구 포함). 2026-10-08 사용자가 구버전→신버전 설치 후 기억·설정 보존을 확인했다. 자동 실행 보존은 확인 대기다. 화면 복원은 2026-10-07 코드에 반영되었다.
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, 새 게이트 테스트(실제 스냅샷·내보내기·검증으로 끝까지 실행 포함)와 시작 연결 테스트, 펫 전체 655 pass / 리눅스 전용 6 fail(변경 전과 같은 목록), Rust 포맷·Windows 대상 엄격 Clippy·테스트 76개, `db-snapshot` 테스트, setup 테스트 55개. 실제 Windows 업데이트·OneDrive·잠긴 파일은 확인하지 않았다.
- 검토 지적 반영(2026-10-07): 위의 고친 버전 이어받기·기록된 백업 보존·깨진 기록·다시 읽기·남은 폴더 정리·여유 공간 세 벌·업데이트 중 백업 거절·오래 남는 줄 숨김. 확인(Linux): 타입 검사, UI·서비스 빌드, 게이트·기록·백업·설정 줄·시작 연결 테스트(새 테스트 12개, 고치기 전 코드에서는 새 게이트 테스트 8개가 실패함을 확인), 펫 전체 667 pass / 리눅스 전용 6 fail(변경 전과 같은 목록; 변경 전 실행에서 네트워크 시간 의존 테스트 1개가 한 번 더 실패했다). Rust는 바꾸지 않았다. 잠긴 파일 정리는 Windows에서 확인해야 한다.

## 화면 백업 내보내기 (2026-10-07, 실제 Windows 확인 대기)

- 연결과 설정 화면의 "백업" 칸에서 이 PC의 기억을 글 형식(`apps/memory` `portable:export`)으로 내보낸다(`src/service/backup.ts`, RPC `backup.export`). 메모리 서버를 멈추지 않는다: 내보내기는 읽기 전용 연결의 한 트랜잭션에서 읽으므로 WAL 스냅샷 시점으로 일관된다(쓰는 중인 다른 연결이 있어도 확정된 기억만 담기는 것을 실제 내보내기로 확인). 백업 중 첨부가 삭제되면 실패할 수 있으며 다시 시도하면 된다.
- 저장 위치: 문서 폴더의 `Bara 백업\bara-backup-YYYYMMDD-HHmmss`(같은 이름이 있으면 `-2`…). 호스트가 Windows 알려진 폴더 API로 문서 폴더를 찾아 서비스에 넘기며, 화면은 경로를 보낼 수 없고 `open_backup_folder`로 그 폴더 열기만 요청한다. 앱 데이터 밖이라 바라를 지워도 남는다. 설정·자격·AI 키는 포함하지 않는다.
- 안전장치: 이 PC에 완료된 설치가 있을 때만(원격·기존 서버 연결이면 버튼이 꺼지고 이유 표시), 한 번에 하나, 업데이트를 마무리하는 중(업데이트 전 백업이나 그 뒤 기억 준비)이 아닐 때만(`BACKUP_UPDATE_RUNNING`), 시작 전 여유 공간 확인(DB+WAL+첨부+200MB), 중단 가능(화면의 "중단"이나 바라 종료로 취소. 2026-10-07 독립 검토 보완부터 설정 화면을 떠나도 계속되고 다시 열면 진행이 이어 보인다). 실패·중단 시 이번 실행의 임시 폴더와, 복사 도중 끊겨 `manifest.json`이 없는 이번 대상 폴더만 지운다. 다른 백업이나 링크는 건드리지 않는다. 실패 원인이 길면(한글 오류 줄 등) 네이티브 호스트의 1000바이트 한도 안으로 줄여 보인다.
- 아직 없는 것: 원격 서버의 백업, 오래된 백업 정리. (화면에서 복원은 2026-10-07 "화면에서 백업 되살리기"로 반영) 원격 서버 백업은 2026-10-08 "7일마다 서버 백업을 받아 두고 최신 2개 유지"로 정했다(설계 전, `decisions/2026-10-08-backup-policy.md`).
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, 백업 테스트 14개(실제 내보내기 프로그램으로 끝까지 실행 포함), 펫 전체 628 pass / 리눅스 전용 6 fail(변경 전과 같은 목록), Rust 포맷·Windows 대상 엄격 Clippy·테스트 76개. 문서 폴더가 OneDrive로 옮겨진 경우, 탐색기 열기, 설정 화면 동작은 Windows에서 확인해야 한다.

## 설치 마법사 보완: 여유 공간 확인과 모델 다운로드 진행률 (2026-10-07, 실제 Windows 확인 대기)

- 이 PC에 새로 준비하거나 중단된 준비를 이어 할 때, 설정·기록·데이터 폴더를 쓰기 전에 데이터 폴더가 있는 드라이브의 여유 공간을 확인한다. 필요량은 모델 약 1.7GB(이미 받은 모델 파일만큼 뺌) + 작업 여유 1GB이며, 부족하면 `INSTALL_DISK_LOW`로 멈추고 더 필요한 양과 지금 여유를 GB로 알린다(`src/service/install/disk-space.ts`). 여유 공간을 읽지 못하면(Bun의 `statfs`가 Windows에서 실패하는 경우 포함) 막지 않고 진행한다. 저장 위치 화면의 "이 PC" 선택에는 "모델 약 1.7GB를 내려받아요. 여유 공간이 3GB쯤 필요해요"를 보여준다.
- 모델 크기 근거: 고정한 파일의 크기(Hugging Face, 2026-10-07 조회) — bge-m3 q8 569.7MB + 토크나이저 17.1MB, SigLIP2 글 283.4MB + 그림 94.7MB + 토크나이저 34.4MB, 리랭커 q8 570.7MB + 토크나이저 17.1MB, 합계 약 1.59GB. 한국어 사전 파일은 크기를 확인하지 못해 100MB로 잡았다.
- 진행률: 한국어 사전과 모델 4개를 받는 스크립트(`apps/setup/src/managed-models.ts`, `apps/memory/scripts/prefetch-core-models.ts`)가 `@@bara-progress {part,parts,loaded,total}` 줄을 내고, 서비스가 이를 엄격히 읽어 한 줄의 순서(1/5~5/5)로 합친 뒤 진행 이벤트의 `detail`로 보낸다. 네이티브 호스트는 네 개의 정수 필드만 다시 만들어 화면에 넘긴다(`policy::progress_detail`). 화면은 "모델 받는 중 (2/5) · 312MB / 570MB"와 진행 막대를 보여주며, 전체 크기를 모르면 받은 양만 보인다. 단계 문구 알림은 단계가 바뀔 때만 낸다. 받은 양은 실제 값이고, 전체 크기는 다운로드 라이브러리가 최신 버전 기준으로 조회한 값이라 대략값일 수 있다. 크기 조회가 실패해도(오프라인 등) 다운로드는 그대로 진행된다.
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, 펫 전체 테스트 612 pass / 리눅스 전용 6 fail(변경 전과 같은 목록), 여유 공간이 부족할 때 데이터 폴더가 그대로 남는 테스트, Rust 포맷·Windows 대상 엄격 Clippy(`--tests`)·테스트 69개, setup 테스트 53개, 진행 줄 헬퍼 테스트 14개. 실제 다운로드와 Windows 화면 표시는 확인하지 못했다(이 환경은 모델 허브 접속이 막혀 있다).

- 독립 검토 후 보완(2026-10-07): (1) 진행 줄이 단계 출력 한도(1MB)에 쌓여, 회선이 느려 다운로드가 2시간 가까이 걸리면 설치가 `INSTALL_OUTPUT_LIMIT`로 끝날 수 있었다 — 서비스가 읽은 진행 줄은 보관·한도 계산에서 빼고, 스크립트는 펫이 `BARA_INSTALL_PROGRESS=1`을 줄 때만 진행 줄을 낸다(설치 CLI 터미널·원격 설치 출력에는 섞이지 않음). (2) 끊긴 다운로드의 임시 파일(`*.tmp.<pid>.*`)을 받은 모델로 세지 않는다. (3) 새 모델 단계의 첫 진행 줄이 앞 단계 마지막 줄 직후라 빠지던 것을 고쳤다.
- 알려진 한계: 한 모델 단계 안에서 전체 크기는 파일을 받기 시작할 때마다 더해진다. 그래서 작은 토크나이저를 받은 직후 막대가 가득 찼다가 큰 모델 파일이 시작되면 다시 낮아질 수 있다. 받은 양 숫자는 실제 값이다.

## 단계 1C③ 종료 정리 (2026-10-07, 실제 Windows 확인 대기)

- 트레이 "바라 종료"는 바로 프로세스를 끝내지 않는다. 트레이 상태 줄을 "바라를 종료하는 중이에요…"로 바꾸고, 호스트 전용 요청 `service.drain`을 서비스에 보낸 뒤 소유 프로세스를 닫는다. 종료가 시작되면 다른 트레이 명령은 무시한다(`src-tauri/src/tray.rs`).
- 서비스는 `service.drain`을 받으면 새 요청을 `SHUTTING_DOWN`(“바라를 종료하고 있어 새 요청을 받지 않았어요…”)으로 거절하고, 실행 중인 작업을 최대 15초(`native-host.json` `contract.serviceDrainMs`) 기다린다. 그때까지 끝나지 않은 작업은 취소하고 2초 더 응답을 기다린 뒤 자신이 시작한 로컬 서버·터널을 닫는다(`src/service/main.ts`). WebView는 이 요청을 보낼 수 없다(`protocol.ts` 비공개 메서드, `policy.rs` 허용 목록 밖).
- 호스트 쪽 기다림도 제한 시간(15초 + 5초)이 있어, 멈춘 서비스가 앱 종료를 막지 못한다. 입력 중이거나 보내는 중인 글은 기존처럼 화면 저장소(초안·보낼 목록)에 남아 다음 실행에서 이어진다. 외부 서버·AI 프로그램은 종료 대상이 아니다.
- 앱을 끝내는 명령은 트레이 "바라 종료" 하나다. 아직 없는 것: Windows 로그오프·시스템 종료 때 같은 정리를 하는 것(그때는 기존처럼 소유 Job이 프로세스를 함께 끝낸다).
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, 새 서비스 테스트 3개(제한 안에 끝나는 작업 대기, 제한에 걸린 작업 취소 응답, WebView의 drain 차단), Rust 포맷·Windows 대상 엄격 Clippy·Rust 테스트 66개, 펫 전체 테스트 실패 목록 변경 전과 동일(리눅스 전용 6건).

## Windows 검토 후 오류 보완 (2026-10-07)

- `maintenance.json`의 첫 쓰기가 실패해도 이번 실행의 버전·경로·배포 정보·설치 ID를 유지해 다음 스키마 기록에서 재시도한다. 실제로 저장된 기록과 저장 예정 기록을 분리하므로 옛 앱 버전과 새 DB 버전이 섞이지 않는다.
- Claude 인증 조회가 `exit 1`과 `loggedIn: false`를 함께 반환하면 로그인 필요로 표시한다. 다른 종료 오류·잘못된 응답·취소·시간 초과는 그대로 구분한다. CLI 테스트는 실제 Bun 프로세스와 Windows `.cmd`/POSIX 실행 파일을 사용해 Windows에서도 실행한다.
- 마법사의 단계 방문마다 유효성을 확인한다. AI 저장·검사 중 이전 단계로 이동하거나 같은 단계에 다시 들어가거나 마법사를 끝내면 이전 방문의 늦은 응답이 화면과 설정 상태를 바꾸지 못한다.
- 펫 위치는 숨겨진 상태에서 복원하되, 복원 오류 알림은 트레이 생성과 최종 표시 모드 적용 뒤에 게시한다. 새 `reason` 응답 필드가 빠져 있던 Windows 테스트 기대값도 수정했다.
- 검증: Windows 전체 Bun **657 pass / 2 skip / 0 fail**(생략은 선택적 실제 모델 평가 2개), CLI 검사 **21 pass / 0 skip**, Rust **86 pass**, 타입 검사·엄격 Clippy·Rust 포맷 검사·UI/서비스/네이티브 빌드 통과. 독립 검토에서 추가 결함 없음.
- 별도 테스트 데이터의 실제 Windows 앱에서 손상된 위치 파일의 오류 말풍선 표시와, 느린 AI 검사 중 **다음 → 이전** 뒤 저장 위치(1/4) 화면 유지까지 확인했다. 기존 사용자 데이터·운영 서버·원격 브랜치는 변경하지 않았다. 설치 파일 배포와 여러 모니터의 배율 검증은 이번 검사 범위에 포함하지 않았다.

## 단계 7A 설치 버전 기록 (2026-10-06, 일부)

- 서비스가 시작할 때마다 데이터 폴더의 `maintenance.json`을 읽어 이번 실행을 `first-run`·`same-version`·`update`·`downgrade`·`unreadable`·`read-failed`·`unversioned`로 나누고 `status` 응답의 `maintenance`로 알린다(`src/service/maintenance/manifest.ts`). 기록에는 설치 ID(처음 한 번 만들고 바꾸지 않음), 앱 버전, 설정 형식, 마지막 DB 스키마 버전(`managed-prepare`가 알려준 값), 배포 묶음 정보, 데이터·자원 경로가 들어가며 비밀값은 넣지 않는다.
- 낮은 버전으로 실행했거나(`downgrade`), 읽었지만 알 수 없는 기록(`unreadable`, 더 새 형식일 수 있음), 일시적으로 읽지 못한 기록(`read-failed`, 백신 잠금 등), 앱 버전이 `MAJOR.MINOR.PATCH`가 아닌 실행(`unversioned`, 체험판 버전 번호)은 기록을 쓰지 않는다. `package.json` 버전이 이 형식인지 테스트로 막는다. `first-run`은 "기록 없음"이지 "데이터 없음"이 아니다(기록 이전 설치도 처음 한 번은 `first-run`). 기록을 쓰지 못해도(잠긴 폴더 등) 앱은 멈추지 않고 다음 시작에 다시 시도한다.
- 후속 반영(2026-10-07): `maintenance/upgrade.ts`가 낮은 버전·알 수 없는 기록·계속 읽지 못하는 기록이면 로컬 DB를 준비하기 전에 `UPDATE_VERSION_UNSAFE`로 차단한다. 앱 전체 실행이나 설치기의 설치 동작을 막는 기능과는 다르다. 남은 것: NSIS 설치 단계의 다운그레이드 거절·파일 교체 연동, 같은 버전 수리, 원격 설치의 DB 스키마 기록.
- 작업 분담: 구현은 하위 에이전트(Sonnet), 검토·보완(기록 실패가 앱 시작을 막지 않도록 변경)은 이 세션.
- 확인한 것(Linux): 타입 검사, 서비스 빌드, 새 테스트 15개 통과, 펫 전체 테스트 실패 목록 변경 전과 동일(Windows 전용 검사).

## 단계 2 첫 실행 설정 마법사 (2026-10-06, 실제 Windows 확인 대기)

- 메인 창의 새 화면 `onboarding`(`onboarding.ts`)이 저장 위치 → AI → 확인 → 표시 방식 네 단계를 보여준다. 각 단계는 설정 화면의 부품(`renderConnection`, `renderAiSettings`, `renderAutoStart`)을 그대로 쓴다. MCP·Discord 같은 선택 연결은 아직 기능이 없어 단계로 노출하지 않는다.
- 진행 단계는 메인 창 저장소의 `bara.pet.onboarding.v1`에 남긴다(`onboarding-model.ts`). 어디서 이어 갈지만 정하며, 서버 준비가 끝났는지는 기존 설치 기록(`managed-install.json`)이 판단한다. 저장된 연결 정보가 없으면 언제나 1단계부터, 연결 정보가 있는데 기록이 없으면(마법사 이전에 설정한 경우) 마법사를 다시 띄우지 않는다.
- 3단계는 기억 저장소(`connection.test`), 답변 AI, 기억 정리 AI를 각각 확인한다. 고르지 않은 AI는 "나중에 연결"이다. 테스트 메모는 만들지 않는다.
- 4단계의 "펫으로 보기/트레이로만 사용"은 새 호스트 명령 `set_display_mode`(트레이 토글과 같은 `tray::apply_display_mode`)로 적용하고 저장한다. 자동 실행은 기존 설정 화면과 같은 방식으로 앱 전체에 적용한다.
- 디스크 여유 공간 사전 확인과 모델 다운로드 진행률은 2026-10-07 반영(위 "설치 마법사 보완" 절).
- 확인한 것(Linux, 7A 작업분과 분리한 작업 사본): 타입 검사, UI 테스트 235개, UI 빌드, Rust 66개, Windows 대상 엄격 Clippy 통과.
- 직접 확인하는 법: 마법사는 연결 정보가 없는 새 데이터 폴더에서만 처음부터 열린다. 기존 데이터를 건드리지 않으려면 환경 변수 `BARA_PET_DATA_DIR`를 빈 폴더로 지정해 실행한다.

## 단계 4 AI 탐지와 선택 (2026-10-06, 실제 Windows 확인 대기)

- `ai.discover`(서비스 `ai-discovery.ts`): 정해진 로컬 주소 네 곳(Ollama 11434, LM Studio 1234, Jan 1337, llama.cpp 8080)만 2초 제한으로 동시에 확인하고, Claude Code·Codex는 실행 파일이 PATH에 있는지만 본다(실행·로그인 확인 없음). 응답 없는 후보 하나가 전체를 붙잡지 않는다.
- 설정 화면의 AI 부분을 `ai-settings.ts`로 분리했다. 찾은 서버를 누르면 답변 AI로 고르고 모델은 목록에서 고른다. 주소·모델 직접 입력과 모델 불러오기는 "고급 설정"으로 옮겼다. 저장한 모델이 목록에서 사라지면 "(지금 목록에 없음)"으로 남겨 조용히 바뀌지 않게 했다. 연결 화면(`renderConnection`)과 자동 실행(`renderAutoStart`)도 단계 2 마법사에서 다시 쓰도록 분리했다.
- `AiProbeResult.reason`(`not-configured`·`not-installed`·`login-required`·`connection-failed`·`model-missing`·`unsafe-version`)을 추가했다. 저장 뒤 답변 AI와 기억 정리 AI를 각각 확인해 "저장했고 사용할 수 있어요"/"저장했지만 아직 쓸 수 없어요"를 따로 표시한다. Codex 로그아웃과 CLI 미설치를 각각의 문구로 구분한다.
- 작업 분담: 서비스 쪽 구현은 하위 에이전트(Sonnet), 화면·통합·검토는 이 세션이 했다.
- 확인한 것(Linux): 타입 검사, UI·서비스 빌드, UI 테스트 235개 통과. 펫 전체 테스트를 임시 메모리 보관소로 돌리면 534개 통과·6개 실패이며, 6개는 이전부터 있던 Linux 전용 실패(SSH·Windows 경로)다. 이 과정에서 기존 테스트 1개가 새 `reason` 필드 때문에 깨진 것을 찾아 고쳤다. Rust 66개, Windows 대상 엄격 Clippy 통과.
- 확인하지 못한 것: 실제 Windows에서 탐지(특히 PATHEXT를 쓰는 `Bun.which`), Claude·Codex 로그인 필요 판정, 설정 화면 동작.

## 단계 1B 펫 숨김 유지와 숨긴 동안의 표시 (2026-10-06, 실제 Windows 확인 대기)

- 트레이에서 고른 표시 상태를 `pet-display.json`(데이터 폴더, 펫 위치 파일 옆)에 저장하고 다음 실행에 복원한다(`app_visibility.rs`). 파일이 없거나 읽지 못하면 펫을 보인다. 읽기·저장 실패는 각각 말풍선으로 알린다(`HOST_DISPLAY_MODE_READ_FAILED`, `HOST_DISPLAY_MODE_SAVE_FAILED`).
- 시작 순서를 트레이 생성 → 펫 표시로 바꿨다. 트레이를 만들지 못하면 기존처럼 시작 오류로 앱이 끝나므로 숨긴 채 보이지 않는 실행이 남지 않는다. 펫이나 복구 창을 띄우는 설계안은 트레이 없이 종료할 수단이 없어 보류했다.
- 펫이 숨겨진 동안 입력창·말풍선은 사용자가 마지막으로 누른 트레이 아이콘 위치(없으면 마우스 위치, 그것도 없으면 주 모니터 오른쪽 아래)를 기준으로 그 모니터의 작업 영역 안에 놓는다. 숨기거나 보일 때 열린 입력창·말풍선도 새 기준으로 옮긴다.
- 결과에 `origin`(`user`/`background`)을 붙였다. 펫이 숨겨진 동안 `background` 결과(시작 시 연결 확인 실패, 펫 위치 복원 실패 등)는 말풍선을 띄우지 않고 "최근 결과"에 보관하며 트레이 첫 줄을 "바라 실행 중 · 확인할 결과 있음"으로 바꾼다. "최근 결과"를 열면 원래 문구로 돌아간다. 펫이 보일 때와 사용자가 요청한 결과는 기존과 같다.
- 확인한 것(Linux 개발 환경): 타입 검사, UI·서비스 빌드, UI 테스트 224개 통과, 펫 전체 테스트 실패 목록 변경 전과 동일(Windows 전용 검사). Rust 테스트 66개(새 검사 포함) 통과, `cargo fmt --check`, Windows 대상 `clippy --tests -D warnings` 통과.
- 확인하지 못한 것: 실제 Windows에서 숨긴 채 재실행, 숨긴 상태의 입력창·말풍선 위치(배율·여러 모니터 포함), 숨긴 상태에서 시작 연결 실패 시 트레이 문구 변화.

## 단계 1A 트레이 메뉴 (2026-10-06, 실제 Windows 일부 확인)

[실행 계획](decisions/2026-10-04-onboarding-tray-plan.md) 단계 1A를 코드에 반영했다. 트레이 메뉴는 상태 줄(바라 실행 중)·입력·검색·대시보드·설정·최근 결과·펫 숨기기/보이기·바라 종료다. 왼쪽·오른쪽 클릭 모두 메뉴만 열고, 예전처럼 클릭할 때 큰 창을 함께 띄우지 않는다.

- 입력창 열기 규칙을 `overlay::quick_action`으로 분리했다. 펫 클릭만 열린 입력창을 닫고, 트레이·메인 창의 열기는 항상 열고 초점을 준다.
- 대시보드 열기(`open_dashboard_with`)와 설정 열기(`show_panel_mode`)를 기존 명령과 트레이가 함께 쓴다. 관리자 링크는 여전히 호스트 안에서만 다룬다.
- 최근 결과는 펫의 기존 동작과 같이 현재 결과, 없으면 마지막 답변을 다시 보여준다(`feedback::show_last`).
- 트레이 명령 실패는 `contract.trayErrorEvent`로 메인 창에 전달하고, 메인 창이 `messages.hostErrors` 문구로 말풍선을 띄운다.
- 1A 당시에는 펫 숨기기가 이번 실행에만 적용됐다. 이후 1B에서 숨긴 상태 저장·복원과 트레이 기준 배치, 1C에서 그리기 중단·시작/종료 조정을 반영했다(위 해당 항목 참고).
- 확인한 것(Linux 개발 환경): 타입 검사, UI·서비스 빌드, UI 테스트 223개 통과. 펫 전체 테스트는 변경 전후 실패 목록이 같다(남은 실패는 DPAPI·SSH 등 Windows 전용 검사). Rust 테스트 60개(Linux에서 컴파일되는 범위, 새 검사 3개 포함) 통과, `cargo fmt --check` 통과, Windows 대상(`x86_64-pc-windows-gnu`) `cargo check`와 `clippy --tests -D warnings` 통과.
- 사용자 Windows 확인(2026-10-06): 트레이 클릭 시 메뉴만 한 번 열림, 트레이에서 연 입력창 유지, 대시보드 열림, 펫 숨기기·보이기 동작.
- 결정: 입력창이 열린 채 트레이 아이콘을 누르면 기존의 바깥 클릭 규칙으로 입력창이 닫힌다(초안은 유지, "입력"으로 다시 열림). 사용자 결정으로 이대로 둔다.
- 해결: 트레이 메뉴 위에서 마우스 포인터가 보이지 않던 문제. 다른 앱의 트레이 메뉴는 정상이고 펫을 숨겨도 생겼다. `tray-icon`의 숨은 메뉴 소유 창에 클래스 커서가 없어서로 보고 그 창에 기본 화살표 커서를 지정했다(`tray.rs` `arrow_cursor_for_tray_window`). 사용자 Windows에서 해결을 확인했다.
- 확인하지 못한 것: 실패 말풍선, Windows 전용 Rust 테스트(`cargo test` 77개).

## 날다람쥐 Spine·사용성 개선 메인 반영 (2026-10-04)

설계는 [날다람쥐 Spine 설계](decisions/2026-10-04-squirrel-spine-design.md)이며 `18bd5d38`까지의 작업을 `main`에 병합했습니다. 실행과 Spine 내보내기는 메인 저장소의 `apps/pet`에서 이어갑니다. 기존 작업 사본의 `.omx/dev-data`도 이 폴더로 옮겨 연결 정보와 초안을 유지합니다.

병합 검증: 작업 사본과 메인 폴더에서 펫 전체 테스트 각각 562 통과·선택적 실제 AI 평가 1개 생략·실패 0, Rust 77개·엄격 Clippy·타입 검사 통과. 메인 폴더의 UI·서비스·네이티브 빌드도 통과했습니다. 작업 기록·검증 자료 1,285개와 메인에 먼저 있던 Spine 파일 69개를 해시 확인 후 보존했으며, 별도 메모리 인증 파일은 메인 데이터와 섞지 않고 로컬 백업에 보관했습니다.

- 펫 창은 예전 새 SVG 대신 캔버스 하나에 날다람쥐를 그립니다. 앱 상태(작업 중, 저장, 기억을 찾은 답변, 실패, 10분 동안 상호작용 없음)에 따라 몸통 동작과 표정이 바뀌고, 시작할 때 창 위쪽에서 작게 날아와 자리에 앉습니다. 앱·트레이·설정 창 아이콘은 사용자 제공 다람쥐 이미지입니다.
- 펫 아래 입력·질문 바로가기 버튼을 제거했습니다. 펫을 눌러 입력창을 열고 그 안에서 입력·질문을 선택합니다. 발아래 동작을 담는 30px 하단 여백은 유지하며 `--pet-floor-inset`에서 읽습니다.
- 바로가기 제거 검증: 타입 검사·UI 빌드·캐릭터 및 오류 문구 테스트 81개 통과. 실제 Windows 펫 창에서 버튼 제거와 캐릭터 배치를 확인하고, 펫 클릭으로 입력창 열기·질문 모드 전환을 확인했습니다. 전후 화면은 `.omx/e2e/pet-shortcuts/`에 보관합니다.
- 입력창은 펫 재클릭·창 바깥 클릭·Escape로 숨기며 초안은 유지합니다. 입력창에서 펫으로 초점이 옮겨질 때 먼저 닫았다가 같은 클릭으로 다시 열리는 경합을 피하고, 입력창 내부의 입력·질문 전환은 유지합니다.
- 입력창 닫기 검증: 타입 검사·UI 빌드·관련 Bun 테스트 66개·Rust 테스트 77개·엄격 Clippy 통과. 별도 데이터의 실제 Windows 앱에서 재클릭·바깥 클릭·재열기·한글 초안 보존·질문 전환·Escape를 확인했습니다. 화면은 `.omx/e2e/quick-dismiss/`에 보관합니다.
- 우클릭으로 여는 창 상단에 **대시보드 열기**를 추가했습니다. 기존 네이티브 명령으로 저장된 관리자 인증정보를 사용하며, 링크의 토큰은 화면에 반환하지 않습니다.
- AI 설정 저장은 원래 구현되어 있었고, 저장소 재열기·정리 AI 변경 검증에서도 값이 유지됩니다. 저장 안내가 화면 아래에만 있던 문제를 고쳐 저장 버튼 근처에 저장됨·미저장·진행 중·오류를 표시합니다. 첫 호환 API 선택의 빈 주소와 모델 미선택 상태의 모델 목록 조회도 보완했습니다. 기본 Bun 전체 562 통과·선택적 AI 평가 1개 생략·실패 0, 대시보드 링크 5개 검사 통과.
- 사용자 제공 `art/squirrel/icon.png`를 앱·트레이·설정 창·favicon에 적용했습니다. 기존 Tauri CLI로 256·128·64·48·32·24·16px ICO를 만들며, 설정 창에는 원본 PNG를 그대로 포함합니다. `build.rs`는 ICO 변경을 감시합니다. 타입 검사·자산/번들 검사 10개·UI/네이티브 빌드 통과, Windows 디코더의 7개 크기·픽셀/투명도와 실제 제목 표시줄·설정 창 표시를 확인했습니다. 검증 화면은 `.omx/e2e/user-icon/`, 크기별 미리보기는 `.omx/e2e/squirrel-user-icon/`입니다.
- WebGL을 쓸 수 없거나, 그림 파일을 읽지 못하거나, 창 배치가 캐릭터를 담지 못하면(하단 여백 부족, `CAMERA_LAYOUT`) 펫 창에 원인을 적은 오류 카드가 보입니다. 예전 새 그림으로 바꿔 보이지 않으며, 펫을 누르면 입력창은 그대로 열립니다.
- 패키지 앱이 정상 `.atlas`에도 `text/html`을 붙여 파일 없음으로 오인하던 문제를 수정했습니다. 이제 실제 HTML 본문일 때만 `ASSET_MISSING`으로 판단합니다. 원본 저장소에 내보낸 최신 `bara.json`·atlas·PNG와 `bara.spine`을 현재 작업 사본에 반영했고, 검사 84개·타입 검사·UI/네이티브 빌드 및 실제 패키지 앱의 캐릭터 표시를 확인했습니다. 재내보내기 경로는 `art/squirrel/README.md`, 전후 화면은 `.omx/e2e/spine-atlas-fix/`입니다.
- 펫 창의 명령(입력창 열기, 설정 열기, 창 끌기)이 거부되면 창 위쪽 알림 줄에 원인과 함께 보이고, 12초 뒤나 다음 명령이 성공하면 사라집니다(설계 결정 D10). 입력창과 설정 창은 창을 먼저 띄운 뒤 포커스 단계에서 실패할 수 있어서 "열기를 끝내지 못했어요"라고 씁니다.
- 들어간 코드: 움직임 규칙과 카메라 계산(`src/ui/squirrel/motion-*.ts`, `camera.ts`), 입력창 열림·닫힘 알림 이벤트(`pet-quick-visibility`), 답변 결과 값(`answerOutcome`), 렌더러·프레임 루프·파일 읽기·펫 창 화면·알림 줄(`src/ui/squirrel/`), UI 빌드의 그림 파일 복사와 Spine 런타임 라이선스 복사(`scripts/ui-assets.ts`). Spine 런타임은 펫 창만 따로 불러오는 코드 조각으로 나뉘어 다른 창은 읽지 않습니다.
- 확인한 것: `bun run typecheck`, `bun test src tests`, `bun run build:ui` 결과(복사한 그림 파일의 해시가 원본과 같음, `dist/licenses/`의 Spine 라이선스, Spine 코드가 분할 조각에만 있음). 브라우저 미리보기(없는 파일에 404를 돌려주는 임시 정적 서버, 개발 서버도 같음)에서 시작 연출, 그림 파일이 없을 때 "HTTP 404"를 적은 `ASSET_HTTP` 카드, 띠 높이 0일 때의 `CAMERA_LAYOUT` 카드, 명령 실패 알림과 카드가 함께 보일 때 겹치지 않음을 확인했습니다. 실제 Tauri 앱은 없는 파일 요청에 `index.html`을 상태 200으로 돌려주므로, 앱에서는 `ASSET_HTTP`가 아니라 "앱이 그 파일 대신 화면 문서(HTML)를 돌려줬어요"라고 적은 `ASSET_MISSING` 카드가 보입니다(같은 방식으로 응답하는 임시 서버로 확인, 실제 앱에서는 아직 확인하지 않음).
- 남은 것: 실제 Tauri 앱에서의 확인(설계 12절 5번: 상태별 동작, 명령 실패 알림, 창을 숨겼을 때 그리기 정지, 배율이 다른 모니터), 배포 전 AGPL 배포와 Spine 런타임 라이선스를 함께 설명하는 추가 허가 문구(설계 열린 항목 O14).

## 구현한 내용

- Windows 펫·트레이·로그인 자동 실행, 별도 입력줄과 말풍선.
- 입력·질문 구분, 초안과 저장 확인, 원문 보기와 분류 수정.
- 로컬 AI 답변, 제한된 Codex·Claude Code 실행, 검토가 필요한 정리 제안.
- 로컬 메모리 서버 준비, 기존 서버 연결, SSH를 통한 새 Ubuntu 서버 설치.
- DPAPI 인증정보, 서버별 인증정보 결합, SSH 지문 확인과 전달 포트 소유권 확인.
- 바라 서버의 연결 정보 API, 분류 검증, 저장 확인 권한, 원문 직접 연결.

## 수집한 실제 증거

- 임시 실제 바라 서버·SQLite·DPAPI·MCP를 이용한 통합 검증.
- 실제 Ollama 답변과 도구 실행을 제한한 Codex 정리 제안. 제안이 자동 승인되지 않음을 확인.
- Windows 실제 창에서 새 데이터 디렉터리로 로컬 설치한 뒤 메모 저장·질문 검색·원문 열기.
- WSL Ubuntu x64의 별도 SSH 서버에서 설치·서비스 시작·저장·검색·재접속·기존 연결 등록.
- 잘못된 지문 거부, 이미 점유된 로컬 포트에 인증 헤더를 보내지 않는 검사.
- 실행 환경을 다른 폴더로 옮긴 뒤 SQLite 라이브러리 로드와 파일 해시 확인.

실행 중 생성한 자세한 검증 기록은 커밋하지 않는 `.omx/e2e`에 보관합니다. 최종 배포 기록에는 재현 명령과 결과를 요약합니다.

## 완료한 설치 검증

- 작은 입력줄의 자동 초점, 말풍선에서 상세 결과·원문 열기와 수정.
- 개발 경로를 제외한 NSIS 설치·실행, 설치된 ONNX·CRT 라이브러리 로드.
- 재실행 후 인증정보·기억 보존, 중복 실행 방지, 자동 실행 등록.
- 제거 뒤 DB·설정·인증정보 파일 5개의 해시 보존과 자동 실행 해제.
- 독립 코드 검토, 기본 테스트와 실제 AI·SSH·서버 전환 통합 검사.

정확한 테스트 수와 재현 범위는 [0.1.0 검증 기록](verification.md)에 있습니다. 바라 서버의 대응 변경은 예전 서버 저장소의 풀 리퀘스트로 들어갔고, 지금은 이 저장소의 `apps/memory`에 합쳐져 있습니다. 새 로컬·원격 설치에는 서버 소스가 포함되며, 기존 바라에 연결할 때는 서버도 호환 버전으로 업데이트해야 합니다.

설치 파일은 코드 서명되지 않았습니다. 새 Windows 가상머신과 실제 ARM64 장비 실행은 검증하지 않았습니다. Linux ARM64 실행 파일은 패키지에 준비하며, 실제 원격 설치 검증 대상은 Ubuntu x64입니다. Claude Code의 실제 호출은 호스트 인증 문제로 성공 검증에서 제외했습니다. 운영 A1은 2026-10-08에 펫 방식으로 옮겼습니다("백업에서 시작"으로 새 설치, `bun run deploy:a1`로 개발 반영, 펫이 자기보다 낮은 서버 버전을 업데이트).
